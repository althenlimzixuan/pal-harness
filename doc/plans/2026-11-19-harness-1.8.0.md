# pal-harness 1.8.0: plan

**Design:** `doc/specs/2026-11-19-harness-1.8.0-design.md` (approved 2026-11-19).
**Branches:** four, one per design part, each cut from the newest `origin/dev` after the previous
part merges: `feature/harness-1.8.0` (this plan, the design and Part A), `feature/harness-1.8.0-b`,
`feature/harness-1.8.0-c`, `feature/harness-1.8.0-d` (Part D and the release files).

## Summary

1. Tasks: Part A (tasks 1–4), Part B (5–7), Part C (8–11), Part D and the release files (12–15),
   the promotion (16) and the clean-up (17).
2. Repo: pal-harness only. No project's pin changes.
3. Approach: inline, part by part. One repo; each part is rule text plus at most one small Go change.
4. Proof: `go vet ./...` and `go test ./...` (what `ci.yml` runs), with `go test -coverprofile`
   holding the 80% gate. Local runs set `GOFLAGS=-p=1 GOMEMLIMIT=2GiB`.
5. Tests grow part by part: `TestHarness180Rules` gets one block per part, added red before that
   part's text. The version stays 1.7.0 until Task 16, so `TestCITemplateWiring` holds until then.
6. Risks: the `utf8` gate step only runs for real from the `v1.8.0` tag, in a project's CI; the
   workflow test checks its place and wiring. The 250-line cap on the phase skill: the Company mode
   pointer is paid for by a trim in the same commit.

## Gate dry-runs

No task uses a grep or lint gate beyond the repo's own vet and tests; each new test runs red first.

## Deletes and locks

none: no task deletes a file or takes a lock. `utf8` only reads files.
