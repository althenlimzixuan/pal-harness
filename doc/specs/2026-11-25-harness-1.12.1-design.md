## Questions and answers

All 8 answered "recommended" by the owner on 2026-11-25.

1. **Where does the seed-file rule for "first message" steps live?** [#98] **A (recommended):** in
   `qa.md` section 2 as a fixed rule, and in the spec template's test script as a note on how such a
   step is checked in QA. The step stays in the owner's staging test. B: only in `qa.md`.
2. **How long may an implementer's report be?** [#99] **A (recommended):** a new
   `templates/implementer-report.md` that every brief points to: one pass, at most 60 lines, ending
   with the line `End of report.`, and long output (a full test log) saved to a file the report
   names. A report that repeats a section it already sent is a cut-off at once. B: a line in the
   brief only, no template.
3. **How is "test first" made a gate?** [#100] **A (recommended):** the report's first section is
   **Gate 1 — test first**, and the implementer commits the failing test alone
   (`Add failing test for <behaviour>`) before the code commit. The controller checks the order with
   `git log --name-only`: a code file in the test commit, or a test commit after the code, sends the
   task back (a fix round). B: the report section only (self-declared, nothing to check).
4. **Where does the plan say where a value comes from?** [#101] **A (recommended):** a
   **Values from data:** line in the plan template's task block, and a new `pal-review-plan` check
   (21) plus harness-list item 11: each value a task puts into built text names its source field and
   type. A missing source is a major finding. B: only the reviewer check.
5. **What if `pal-work automation` fails?** [#102] **A (recommended):** exit 4 is run once more,
   like `mode`; a second exit 4 opens the note with one line, `Automation: could not read (exit 4:
   <its message>)`. Exit 5, no `Work CLI:` line or Pal Center older than 0.27.0 skip it silently.
   B: skip on any failure.
6. **Two Windows jobs at once?** [#103] **A (recommended):** a second runner on the same PC with the
   same `pal-pc` label is an owner-run handover in `devops_cicd.md` (it installs a Windows service);
   the queue line divides by the online runners. The 1.12.0 queue line already shows the queue.
   B: only the queue line, no second runner.
7. **How does Codex learn precondition and likelihood?** [#104] **A (recommended):** the session
   writes `precondition:` and `likelihood:` beside each Codex major or critical it rates, and a
   sub-second race in a command-only tool is never critical (`workflow.md`, `review.md`); a Pal
   Center issue asks for the same fields in the Codex prompts. B: only the Pal Center issue.
8. **How is a background test run caught?** [#105] **A (recommended):** the report's **Gate 3 —
   full test run** line gives the command, `foreground` and its exit code; the controller copies it
   into sdd's ledger as `Task K: tests <command>, foreground, exit N`. A missing line, or one that
   says background or has no exit code, sends the task back before the task reviewer. B: the brief
   line only.

## Summary for the owner

1. **QA can pass a "first message" step on the seed file.** When the QA copy cannot open sessions
   (its folders are untrusted), the step's evidence is the session's seed file, and the QA summary
   says so. You still check that step yourself in the staging test.
2. **Implementer reports are one short pass.** Every report follows one template: three gates, at
   most 60 lines, ending `End of report.`. A report that starts repeating itself is stopped at once.
3. **Test first is checked, not trusted.** The failing test is its own commit, before the code. The
   session checks the commit order before the task review.
4. **Plans name where each value comes from.** A task that builds text from data (a line naming a
   repo) lists each value's field and type. The plan reviewer treats a missing one as major.
5. **`/pm` opens with Pal Center's automation summary.** Right after the mode check, `/pm` and
   `/pm pickup` read `pal-work automation` and start the note with its lines, as they are.
6. **Two Windows CI jobs at once.** A handover adds a second runner on your PC, and the queue
   estimate counts runners.
7. **Codex severities show their odds.** Every Codex major or critical carries its precondition and
   likelihood, and a sub-second race in a command-only tool is never critical.
8. **Background test runs are caught.** The report states the full test run's command, that it ran
   in the foreground, and its exit code; the controller logs it in the ledger.

## Changes

Issue numbers in brackets are in ai-workshop. Everything ships in one PR into `dev`. `subagents.md`,
`review.md` (150 of 150) and the pm `SKILL.md` (250 of 250) are at their caps: their changes are

### A. Seed-file evidence for "first message" steps [#98] (`skills/phase/references/qa.md` section 2, `templates/spec.md` test script)

**Problem.** In Pal Center phase 024 (retro item 5), the QA copy could not open sessions until its
folders were trusted, so steps 1-2 ("first message") were shown on the seeds the code writes, not in
a live session. Each phase decided on its own what counted as evidence.

**Rule.** Answer 1.
1. A step whose expected result is what a started session receives first (its first message, the
   notes it is handed) passes in QA on the session's seed file when the QA copy cannot open the
   session (the folder is untrusted, or Claude Code is not signed in there). The session reads the
   seed file under `%APPDATA%\PalCenter\sessions\` (or the QA copy's own data folder) and compares
   its text with the step's expected result.
2. The `summary.md` row says `evidence: seed file <path>` and quotes the matching lines. It is a pass,
   never a skip.
3. The step stays in the owner's staging test, where sessions open for real.
4. The spec template's test script says that such a step is checked on the seed file in QA.

### B. One report shape for implementers [#99, #100, #105] (new `templates/implementer-report.md`; `skills/phase/references/subagents.md` sections 1 and 2)

**Problem.** In Pal Center phase 023, one implementer repeated its report until it was stopped, one
wrote its code before its test, and two ran the full test run in the background although the brief
said not to. Each rule was a line in the brief that nothing checked.

**Rule.** Answers 2, 3 and 8. The brief points every implementer and fixer to
`.pal-harness/templates/implementer-report.md`. The report has, in order:
1. **Gate 1 — test first:** the test commit's hash and message (`Add failing test for <behaviour>`),
   which holds only tests and fixtures, and is made before any code commit (only a Carry-over commit
   may come earlier); the command run and the
   lines that name each failing test. A guard test reports `RED by mutation: <test>` here instead.
2. **Gate 2 — green and lint:** the commands, and their exit codes.
3. **Gate 3 — full test run:** `Full test run: <command>, foreground, exit <N>`; a timeout is a failure.
4. **Checks:** Known findings checked, Carry-over fixed, QA checks run, nothing left running.
5. **Changes:** commits and files, one line each.
6. **New question** (only when item 6 of the brief applies).
7. The last line, `End of report.`. Nothing follows it, and nothing is sent after it.

At most 60 lines. Long output (a full log) goes in a file under the task's worktree, and the report
names it. The controller:
- checks Gate 1 with `git log --name-only <base>..HEAD`: the test commit comes before the task's
  code and has no code file. A code file in it, or the code before the test, is a fix round;
- copies Gate 3 into sdd's ledger as `Task K: tests <command>, foreground, exit N`. A report with no
  Gate 3 line, `background` in it, or no exit code goes back before the task reviewer;
- treats a report that repeats a section it already sent, or runs past `End of report.`, as a
  cut-off at once (section 2 item 1), not on the second time.

### C. Values from data [#101] (`agents/review-plan.md` check 21 and harness-list item 11; `templates/plan.md`; `skills/phase/references/plan.md`)

**Problem.** In a Pal Center plan, a task built a line naming a repo without saying which field held
the repo (a `project.yaml` component path, or the GitHub `owner/name`). Round 1 found it as a major.

**Rule.** Answer 4. A task that builds text from data (a message, a label, a path, a command line, a
log line) has a **Values from data:** line: each value it puts in, with its source field and type
(`project.yaml components[].repo`, string `owner/name`). `pal-review-plan` check 21: a value with no
source, or a source that does not exist (Grep it), is a major finding. The harness list's item 11
names it, so round 1 always checks it.

### D. The automation summary in `/pm` [#102] (`skills/pm/SKILL.md` **Mode first** and **Start-of-session note**)

**Problem.** Pal Center decision 110 (phase 024) put the automation summary in every session Pal
Center starts, through the seed file, and left sessions the owner starts by hand to a harness note.

**Rule.** Answer 5. Right after `mode`, `/pm` and `/pm pickup` run
`pal-work automation --project <key>` (Pal Center 0.27.0 or later, from the `Pal Center version:`
line). The start-of-session note (and pickup's first message) opens with its numbered lines, as they
are, before its own lines. Exit 5, no `Work CLI:` line or an older Pal Center: skip it, with no
line. Exit 4: run it once more; a second exit 4 opens the note with
`Automation: could not read (exit 4: <its message>)`.

### E. Two runners for Windows jobs [#103] (`practices/devops_cicd.md` **Self-hosted runners** and **One runner, one queue**)

**Problem.** In Pal Center phase 023 a CI run took about 35 minutes, since the one self-hosted runner
(`pal-pc`, `C:\actions-runner`) runs Windows jobs one at a time.

**Rule.** Answer 6.
1. **Second runner (owner-run, once).** A second runner on the same PC, in its own folder
   (`C:\actions-runner-2`), named `pal-pc-2` with the extra label `pal-pc`, installed as a service.
   The jobs' `runs-on` label set (`WINDOWS_RUNNER`) is unchanged, so either runner takes the next
   job. The handover gives the exact `config.cmd` line, with the registration token from
   `gh api -X POST repos/<owner/repo>/actions/runners/registration-token --jq .token`.
2. Two jobs at once share the PC's memory. A run that fails on low memory while both runners are busy
   is re-run once; if it happens again, the owner stops `pal-pc-2`'s service and the queue line goes
   back to one runner.
3. **The queue line** counts the online runners with the label
   (`gh api repos/<owner/repo>/actions/runners`) and writes
   `CI queue: N runs ahead, R runners (about M min)`, with M = 20 × N / R.

### F. Codex severities with precondition and likelihood [#104] (`practices/workflow.md` severity; `skills/phase/references/review.md` section 3)

**Problem.** In Pal Center phase 023, Codex rated a PID-reuse race in a command-only tool as
critical. Its window was under a second, and the session downgraded it after an owner stop.

**Rule.** Answer 7.
1. Every Codex major or critical the session rates is written with `precondition:` (what must be
   true for it to happen) and `likelihood:` (how often, under what timing), in the report and on the
   owner-stop page.
2. A race that needs a sub-second window in a command-only tool (a CLI one person runs, with no
   service and no other user) is never critical: it is minor, or major when it can lose data or
   cross a trust boundary. The downgrade is written with its reason, as today.
3. **Pal Center issue:** the `code` and `uiux` prompts ask Codex for the precondition and likelihood
   beside each severity, with the same rule.
