# pal-harness 1.11.0: held store releases, chores that switch off, and LFPV phase 012's lessons

**Status:** Approved by the owner on 2026-11-24, after "accept all" to the 11 questions the same day.
**Source:** 10 harness notes (ai-workshop#68 to #77): one from Pal Center, one owner rule from the
workspace, and eight from LFPV phase 012's retro. Worked in session HARNESS-work-1QT3BV.
**Delivers:** pal-harness 1.11.0:
- one new command, `pal-harness cpu`;
- rule text for the rest.

It is a minor version because of the new command (answer 1). No state field changes, so Pal
Center's reader is not affected. The `upgrade` command and the automatic re-pin move to 1.12.0.

## Summary for the owner

1. **Store releases wait for you or for the end of the approved work.** Under Company mode, a phase
   deploys the API and builds the app as now, but holds the Play upload or OTA update. The held
   changes go out as one release once nothing approved is left, or when you ask. The handover says
   which of the two started it.
2. **A chore can switch itself off.** A card with `After run: off` goes back to `Chores` after its
   run, and any session moves a chore card back when you ask.
3. **Fewer device-check interruptions.** Test phones' reset commands are allowed once, in the
   project's settings, and the session asks for them at the start, not mid-test.
4. **Apps that block screenshots have a recipe:** read screens with `uiautomator dump`, and use a
   development build that allows capture and unlocks with a test PIN.
5. **Clearer handovers.** Every value you're asked for comes with its exact format. A Terraform
   handover includes `gcloud auth application-default login`, `terraform init` and the project ID.
6. **No speed check on a busy PC.** `pal-harness cpu` checks the load first.
7. **Test summaries cite their sources**, so an overclaim is caught before review.
8. **Jest's Windows start failure (0xC0000142)** is re-run like a low-memory kill.
9. **A subagent told to stand down stays quiet**, and the session finishes its work.

## Changes

Issue numbers in brackets are in ai-workshop. Everything ships in one PR into `dev`.

### A. Held store releases under Company mode [#69] (`skills/phase/references/ship.md`, `skills/phase/references/company-mode.md`, `skills/pm/SKILL.md`, `templates/runbook-android-release.md`, new `templates/held-releases.md`)

**Problem.** Each phase that changes a mobile app ends with a store release (Play upload, store
build registration, OTA update). The owner's rule of 2026-11-24 says that under Company mode, a
store release goes out only (a) when all the project's approved work is finished, or (b) when the
owner asks.

**Rule.** Answers 4 to 7.
1. **When it applies.** The project's `pal-work mode` output says Company mode is on, or the mode is
   unknown (exit 4 or 5, no `Work CLI:` line). With Company mode plainly off, ship releases as it does
   today. The rule covers every app on any platform: a Play or App Store upload, a store build
   registration, an OTA update (`eas update` or a project's own publish command).
2. **Ship holds the release.** Ship promotes, deploys the API and runs its gates, and builds the
   store build from `main` exactly as before. It stops before the upload, registration or OTA
   publish, and adds one row to `doc/releases/held.md` in the SSOT repo (from the new
   `templates/held-releases.md`):

   | Phase | Version | Build | Needs | Notes |
   |---|---|---|---|---|
   | 012-over-the-air-updates | 1.3.0 | (EAS build link) | store | (the What to expect now lines for the phone) |

   `Needs` is `store` when the change touches native code (the publish command says, or the
   phase's plan does), otherwise `ota`. The row goes in the close-out PR. The done message says
   `store release held (N held); it goes out when Approved to run is empty, or when you ask`.
3. **(a) All approved work is finished.** The check runs:
   - after every ship close-out;
   - in every `/pm` and pickup run that finds nothing to claim.

   It passes when `held.md` has rows, the Roadmap board's `Approved to run` column is empty, and no
   phase other than the one closing is in `In flight` or `Waiting on you`.
4. **(b) The owner asks.** In any session of the project ("release the app", "publish now").
5. **One batched publish.** The session that publishes:
   - starts its handover with `Release reason: (a) all approved work is finished` or
     `Release reason: (b) you asked`;
   - publishes only the newest held build, because `main` already holds every earlier change.
     Versions never published are skipped in the store;
   - makes a store release when any row says `store`. Otherwise it makes one OTA update;
   - writes one set of release notes that merges every held row's notes;
   - hands over the owner-run steps of the project's runbook as one numbered list (ship section 0
     step 2);
   - on the owner's "done", clears the rows in `held.md`, and writes the version, track and date
     with the reason to the log.

   Publishing is public, so it never passes on a Company-mode default (`company-mode.md`
   section 3): the owner runs or approves it.
6. **A project runbook that says "every phase ends with a store release"** is overridden under
   Company mode. The harness rule says so, and the session follows the harness. A follow-up LFPV
   backlog issue rewords LFPV's runbook section 9 (answer 7).

### B. A chore card that switches itself off [#68] (`skills/pm/references/chores.md`, `skills/pm/SKILL.md`)

**Problem.** Only a once-only card (no timing line) moves back to `Chores`. The owner moves every
other card by hand, the Harness notes card included.

**Rule.** Answers 2 and 3.
1. **`After run: off`.** A new optional line in the card's body. After the run (and its `Last run:`
   line), the session moves the card from `Chores (Active)` to `Chores`, whatever its timing line:
   `gh project item-edit --id <item> --project-id <p> --field-id <status> --single-select-option-id <Chores>`.
2. **The owner asks.** In any session ("turn the weekly audit chore off"), the session moves the named
   card to `Chores` the same way, and says so in one line.
3. **Never the columns.** The session moves cards only. It never edits the board's columns or their
   options, as today.
4. **The Harness notes card.** Pal Center starts the harness batch, and a HARNESS session doesn't load
   `chores.md`. A Pal Center backlog issue asks the daemon to move the card to `Chores` once the
   batch's PR opens, when the card says `After run: off`. For this batch, this session moves PC's
   Harness notes card to `Chores` when its PR opens.

### C. Device-reset commands allowed once [#70] (`practices/react_native.md` **Device testing**, `skills/phase/references/staging-test.md`)

**Problem.** In phase 012, the auto-mode permission check refused `adb shell pm clear` mid-test.

**Rule.** Answer 8.
1. **The entries.** For each package (production and development variants) and each serial in
   `doc/devices.yaml`, the SSOT repo's committed `.claude/settings.json` holds, under
   `permissions.allow`:

   ```json
   "Bash(adb -s R5CX123 shell pm clear com.example.app)",
   "Bash(adb -s R5CX123 shell am force-stop com.example.app)"
   ```

   It is the committed file because a worktree set doesn't see `settings.local.json`. Serials are
   not secret (`devices.yaml` holds them already).
2. **Asked once, at the start.** The first device test of a session (a device-check task, or the
   staging-test pre-flight) checks the file first. When an entry is missing, the session asks once
   in that message, with the exact lines. On the owner's yes it adds them and commits them with the
   phase's docs. Then reset commands run with `-s <serial>`, as listed.
3. A project that cannot allow them keeps the app's debug-only reset, as today.

### D. Apps that block screen capture [#73] (`practices/react_native.md`, new **Screen-capture protection**)

**Problem.** Ellovia Vault sets FLAG_SECURE on signed-in screens, so screenshots are black. The A26
needed many fingerprint unlocks by hand during the device check.

**Rule.** Answer 9.
1. **Reading screens.** `adb -s <serial> shell uiautomator dump /sdcard/ui.xml`, then
   `adb -s <serial> pull /sdcard/ui.xml`. The screen's text (and the server or phone log) is the
   step's evidence. The QA or device-check summary says `screen text: uiautomator` instead of a
   screenshot.
2. **A development build with capture on.** The development variant (`APP_VARIANT=development`)
   leaves the protection off by a build-time flag, so the device check can screenshot it. A test
   proves the production variant keeps it on.
3. **The unlock-free route.** The development variant also accepts a test PIN, which the session
   types with `adb -s <serial> shell input text <pin>` in place of a fingerprint. A build-time flag
   that the production build cannot set guards it, and a test proves the production build refuses
   it. The unlock is never skipped, and the test PIN is never a real secret. A project adds both in
   a plan task the first time it needs them.

### E. Handovers say each value's format; Terraform's handover is complete [#71, #72] (`templates/plan.md`, `skills/phase/references/plan.md` item 15, `skills/phase/references/ship.md` section 0, `practices/devops_cicd.md`)

**Problem.** The handover asked for "Google account" when the IAM member is `user:<email>`. The
production Terraform folder had never been `terraform init`-ed, and the handover left out
`gcloud auth application-default login`. gcloud's default project on the owner's PC belongs to
another product.

**Rule.**
1. **Each value's format.** Every value an owner-run command or step asks for gives its exact
   format and an example: `user:<email>` (`user:owner@example.com`), a project ID, not its name
   (`lfpv-prod-123`), a region code (`asia-southeast1`).
2. **Terraform handovers** list, in order, with the folder:
   1. `gcloud auth application-default login`, once per PC or after it expires;
   2. `terraform init -backend-config=backend.hcl` (or the project's backend file), when the
      folder has no `.terraform/` yet;
   3. the `plan` and the `apply` with the exact `-var-file`;
   4. the GCP project ID they act on.
3. **`--project` on every gcloud call.** Sessions pass `--project <id>` on every `gcloud` command, and
   the handover's commands do too. The default project on the PC is never trusted.
4. The plan review's check on Owner-run commands (item 15) reads these.

### F. Test summaries cite their sources [#74] (`templates/test-summary.md`, `skills/phase/references/review.md` section 1, `agents/review-tests.md`)

**Problem.** Phase 012's infra summary overclaimed the new tests, and a profiling line said "updates
turned off" when it meant "fixed endpoint list". The reviewers caught both.

**Rule.** Answer 11.
1. Each numbered line of `summary.md`, and each claim in its notes, ends with its source in
   brackets:
   - a report file: `[unit_test.html]`;
   - a command and its exit code: `[make reports, exit 0]`;
   - a file and line: `[infra/x_test.go:40]`.
2. Before dispatching the reviewers, the session reads each claim against its source and corrects it.
3. `pal-review-tests`: a claim with no source, or one its source doesn't support, is a major finding.

### G. Jest exit 0xC0000142 on Windows [#75] (`practices/devops_cicd.md` **Free memory before heavy runs** step 4, `practices/testing.md`)

**Problem.** The mobile report run was killed for low memory, and 5 Jest suites failed with
0xC0000142 (a Windows process-start failure). A rerun was clean.

**Rule.** A Jest suite that fails with `0xC0000142` (or exit code 3221225794 or -1073741502) counts
as a run cut short by low memory: run `pal-harness mem --wait 9m`, then re-run only the failed
suites (`npx jest <their paths> --maxWorkers=2`). It is not a fix round. It is logged as
`process-start failure: re-ran N suites`. The same suites failing again the same way are re-run with
`--maxWorkers=1`. A third time, it is a real failure.

### H. `pal-harness cpu` before the paired speed check [#76] (new command, `practices/testing.md`, `templates/test-summary.md`, `agents/review-tests.md` check 5)

**Problem.** The first paired speed check ran while the owner was gaming. Its results contradicted
each other, and it was discarded and run again.

**Rule.** Answer 10.
1. **`pal-harness cpu [--max 25%] [--for 10s] [--wait 0] [--every 30s]`** measures the whole
   machine's CPU use over `--for` and prints one line:

   ```
   cpu busy: 7% over 10s (maximum 25%): ok
   cpu busy: 63% over 10s (maximum 25%): busy
   ```

   It exits 0 when quiet, 1 when still busy after `--wait`, and 2 when the CPU can't be read or an
   argument is wrong. On Windows it reads `GetSystemTimes`, on Linux `/proc/stat`. Other platforms
   exit 2. Like `mem`, it re-checks every `--every` while it waits.
2. **The speed check** runs `pal-harness cpu --wait 9m` first, in the foreground with a Bash timeout
   of 600000 ms. When it is still busy, the check runs anyway. `summary.md` line 4 records
   `CPU busy: N%`, and a slowdown measured that way is re-run once on a quiet CPU before it counts
   as a finding. `pal-review-tests` check 5 reads that mark.

### I. A subagent told to stand down [#77] (`skills/phase/references/subagents.md` sections 1 and 2)

**Problem.** In phase 012, a reports subagent was cut off, then kept sending handbacks after it was
told to stand down. The session finished the reports itself.

**Rule.**
1. **The brief** (every dispatched agent: implementer, fixer, reviewer, reports) gains: when you are
   told to stand down, stop at once. Send no report, handback or message after it, and stop every
   background command, Monitor and watcher you started.
2. **The controller** stops a cut-off agent with TaskStop as soon as it cuts it off. A cut-off is a
   stand-down, a timeout, or an agent that ran out of context. Anything that agent sends later is
   ignored, unanswered.
3. **The session takes over.** After one cut-off, the session does the rest of that agent's work
   itself, inline, from the last good report. It does not dispatch a fresh agent for it. Section 2
   step 1 (a repeating agent) changes to match: the second repeat is a cut-off.

  - the README command table (`cpu`);
  - `templates/ci.yml` names `@v1.11.0`.

  - `cpu`: quiet (exit 0), busy (exit 1), busy then quiet within `--wait`, an unreadable CPU (exit 2),
    bad arguments (exit 2), and the busy share computed from two samples (idle, kernel, user), with
    the Windows kernel time that includes idle.
- **One PR into `dev`**, with one Closes line per note (#68 to #77). It merges on green CI. Then one
  `[HUMAN GATE]` `dev` → `staging` PR, which you merge. Then `staging` → `main`, the `v1.11.0` tag
  on the merge commit, and the CHANGELOG entry. Codex review is skipped (`pal-review` knows only
  workspace projects), and the PR says so.
- **Follow-up issues** (filed when the PR opens):
