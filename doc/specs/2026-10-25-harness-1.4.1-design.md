**Status:** Draft for the owner's review (owner's answers of 2026-10-25: "accept all").
**Source:** seven harness ideas from LFPV's phase 002 retro (`lfpv-docs`: `specs/002-accounts-sign-in/retro.md`).
An eighth idea (drop "/compact after every reply") is Pal Center code, `pickup_seed.go:56`, and moved to a

**Delivers:** pal-harness 1.4.1, text only (practices, skill references, a template). No Go code change.

## Summary for the owner

1. A new npm advisory in dev tooling no longer fails a phase mid-review: CI reads an allowlist in which
   each entry has a reason and an expiry date. Anything not on the list still fails.
2. Test reports are made by one script, once, after the last review fix, and the Jest HTML report shows
   only this run's results.
3. React Native on Windows: local Android builds are arm64-only at low priority, and a session never
   drops the phone's adb link. Metro always watches files.
4. The `go_api` mock command is the one that works in Pal Center (mocks inside `internal/`).
5. Test scripts give the reason beside any step that is surprising by design, and the "ready for your
   test" message lists the steps instead of only linking to them.

## Changes

Each change lists the problem LFPV hit, the new rule, and the files.

### 1. Dev-tooling npm advisories (`practices/devops_cicd.md`, `practices/testing.md`)

**Problem.** A new high advisory in `zod`, used only by the Expo CLI, failed LFPV's app CI mid-review.
Pal Center hit the same thing a day later (undici, test tooling).

**Rule.**
- The Node audit step is `npx audit-ci --high --config audit-ci.jsonc` (replacing `npm audit
  --audit-level=high`).
- `audit-ci.jsonc` holds an `allowlist`. Each entry names the advisory (GHSA id), its reason, and an
  expiry no more than 90 days out. An expired entry fails CI, so the reason is looked at again.
- When a new high advisory fails CI, the session tries, in order:
  1. `npm audit fix` without `--force`, which fixes most;
  2. if the package only runs in dev tooling (CLI, build, tests) and nothing shipped to users loads it,
     an allowlist entry with its reason;
  3. otherwise it is a real security bug: fix it, or ask the owner if the fix needs a breaking upgrade.
- Allowlisting shipped code is never allowed.

### 2. Test reports in one scripted step (`practices/testing.md`, `skills/phase/references/review.md`)

**Problem.** Reports were made before the review fixes, went stale, and had to be made again. The
jest-html-reporters page embedded the library's demo results, with fake failures.

**Rule.**
- Each project has one report command (`make reports`, or `npm run reports` in a Node-only repo) that
  writes every report the phase needs into the phase's `_test_reports/` folder.
- The session runs it once, after the last review fix, on the final commit. Not before the fixes, and
  not per reviewer.
- For Jest, the suggested reporter is `jest-html-reporter`. A report that shows results other than this
  run's (demo data, a template placeholder) is a stale-report finding. Its pass and fail counts must
  match `summary.md`.

### 3. Android builds on Windows (`practices/react_native.md`, new **Native builds on Windows**)

**Problem.** The first local all-ABI build took 31 minutes and flooded the owner's PC.

**Rule.**
- A local Android build builds arm64 only (`-PreactNativeArchitectures=arm64-v8a`) and runs at low
  process priority.
- All-ABI builds are for EAS only, never local.
- The section notes the 31-minute cost, so no one repeats it.

### 4. Device testing (`practices/react_native.md`, new **Device testing**)

**Problem.** Metro ran in CI mode (no file watching), so a file added in a fix round failed to bundle.
The phone's wireless adb link dropped, and the owner said: never drop it.

**Rule.**
- Start Metro for device tests with file watching (`npx expo start`, never `CI=1` or
  `--non-interactive`).
- A session never runs `adb disconnect` or `adb kill-server`, and never toggles the phone's wireless
  debugging.
- If the link drops, the session reconnects once from the saved device details (the IP and port in
  the project's device notes). If that fails, it stops and asks the owner, giving the device name and
  what it tried.

### 5. Go mocks (`practices/go_api.md`, `practices/testing.md`)

**Problem.** `mockery --all --keeptree` with output in a top-level `mocks/` mirrors the `internal/`
paths, which Go forbids importing. LFPV fell back to flat `mocks/`.

**Rule.**
- Use the setup Pal Center runs: `mockery --all --keeptree --dir internal --output internal/mocks`,
  with the same settings in `.mockery.yaml`.
- Keeping the mocks inside `internal/` is what makes the mirrored paths importable.
- `make mock` runs it.

*My call:* the note asked to remove `--keeptree`. The working fix is the output folder, and the tree
stays useful, so the flag stays.

### 6. Surprising steps (`skills/phase/references/spec.md`, `templates/spec.md`)

**Problem.** The owner was surprised that the same email can ask for a code in another language.
That is by design (no account guessing), but the test script did not say why.

**Rule.** A test-script step whose expected result is correct but likely to surprise the owner says why,
in the step itself: "→ you see X (by design: reason)". The spec template shows one example.

### 7. "Ready for your test" lists the steps (`skills/phase/references/staging-test.md`)

**Problem.** The message linked the script, and the owner had to ask "what's the steps?".

**Rule.**
- The in-session "ready for your test" message lists each bundle feature's numbered steps inline (do →
  expect), then the link.
- The phone notification stays short: "needs you: phase NNN is ready for your test — N steps".
- With Pal Center's Work tab, the steps are also there, and the message says so.

## What sessions do differently (the owner's check)

| # | What you'll see | Where to try it |
|---|---|---|
| 1 | A dev-tooling advisory gets an `audit-ci.jsonc` entry with a reason and an expiry, not a red phase | LFPV (`mobile_app`), Pal Center (`desktop`) |
| 2 | One `make reports` run after the last fix; the Jest page shows only real results | LFPV's next phase |
| 3 | A local Android build is arm64-only and does not freeze the PC | LFPV or ETP mobile |
| 4 | Metro picks up new files without a restart; the session never drops or toggles adb | LFPV or ETP device QA |
| 5 | `make mock` works in a fresh Go project | the next kickstarted project, or LFPV `api` |
| 6 | Surprising steps carry "(by design: …)" | any spec |
| 7 | The ready-for-test message lists the steps | any phase with a staging test (LFPV, ETP) |

A project sees these only after it re-pins to 1.4.1 (Pal Center, ETP), or to 1.4.x for LFPV, which is
on an older pin. Re-pinning stays a separate step the owner chooses.
