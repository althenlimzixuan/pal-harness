# pal-harness 1.5.1: Pal Center's phase 010 and 011 notes

**Status:** Approved (owner's replies of 2026-11-09: "accept all" to the questions, "approve" to
the design).
**Source:** 10 harness notes from Pal Center's phase 010 and 011 retros, filed as
althenlimzixuan/ai-workshop#19 to #28 and started from Pal Center's Start work (session
HARNESS-work-59W5MV).
**Delivers:** pal-harness 1.5.1: rule text only (practices, phase and quick-fix skill text, reviewer
agents, the spec template). It is a patch version because no command changes. 1.6.0 stays free for
the planned `upgrade` command.

## Summary for the owner

1. **Windows-security tests check the right thing.** DACL tests compare SIDs and access rights, not
   printed names, and each test sets up and checks its own preconditions.
2. **CI watching survives low memory.** Sessions wait on CI with short foreground waits, never a
   background watcher.
3. **Plan reviews start from past majors.** Round 1 checks the major and critical findings earlier
   plan reviews and owner batches raised, plus a short fixed list, so one plan does not take 3 rounds.
4. **Windows-security tests run as the runner's account before the PR.** A phase that touches them
   runs them once as a standard user in session 0 before its PR, not only in your own session.
5. **Specs that cross accounts get a Trust boundaries table.** Who writes each input, who reads it,
   as which account and on which desktop, what stops misuse and what does not. A critical like
   phase 011's decision 33 now shows up in the spec.
6. **A mid-build request has a short path.** A small request becomes a recorded task without a full
   plan re-review. A bigger one becomes a new card.
7. **A Defender block on a Pal Center CLI is handled.** The session goes on without that CLI and gives
   you the exclusion command once. The Setup step, the new-PC checklist line and signing go to Pal
   Center's inbox.
8. **Local Go tests use less memory.** Each local Go test run uses one package at a time and a 2 GiB
   memory limit, so subagents are not killed mid-task.
9. **A fix round runs the full checks.** The repo's full lint, typecheck and tests, not one file,
   before the round counts as done.
10. **No security promise without what enforces it.** Specs, plan reviews and the security review
    flag absolute wording ("cannot override", "guarantees") that nothing enforces.

## Changes

Each change lists the problem a project hit, the new rule and the files. Note numbers are in
brackets (the list at the end).

### 1. Windows security tests [19] (`practices/testing.md`)

**Problem.** In Pal Center's phase 011, four Windows ACL and window-station tests passed in your
interactive session and failed on the self-hosted runner (`ghrunner`, a standard user, in session
0). The tests compared DACLs by their printed form, and x/sys's `String()` includes the owner and the
group, which differ between accounts. One setup precondition held only by accident.

**Rule.** A new **Windows security tests** section in `testing.md`:
- Assert a DACL ACE by ACE: the ACE type, the trustee's SID (compared as a SID, `EqualSid` or its
  `S-1-…` string), the access mask and the inheritance flags. Never compare a security descriptor's
  `String()`, a whole SDDL string or an account name: the owner, the group and the names change with
  the account, the machine and the language.
- Every precondition a test relies on (a folder exists or not, inheritance on or off, the caller's
  groups, a privilege) is set up by the test and asserted before the step under test.
- A test that needs something session 0 lacks (an interactive window station or desktop) checks for
  it and skips with the reason (`t.Skip("needs an interactive window station; session 0 has none")`).
  The skip is listed in the test summary.

### 2. Watching CI in the foreground [20] (`practices/devops_cicd.md`, `skills/phase/references/build.md`, `review.md`, `signoff.md`, `skills/pm/SKILL.md`)

**Problem.** In phase 011, Claude Code killed two background CI watchers for low system memory while
the self-hosted runner built on the same PC. The session lost its CI watch and polled by hand.

**Rule.** A new **Watching CI** bullet in `devops_cicd.md`, used everywhere (your answer 2):
- Watch with `gh pr checks <n> -R <owner/repo> --watch --interval 30` as a foreground command with a
  Bash timeout of 540000 ms (9 minutes). If it times out with checks still pending, run it again. A
  workflow run started by hand is watched the same way with `gh run watch <id> -R <owner/repo>
  --interval 30`.
- Never watch CI with `run_in_background`, Monitor or a background loop.
- Read the result from the command's exit code.

Every `--watch` line in the skill text points to this bullet.

### 3. The plan reviewer starts from past majors [21] (`agents/review-plan.md`, `skills/phase/references/plan.md`)

**Problem.** Phase 011's plan took three review rounds, each with a major. All three were the same
kind of risk: the owner's daemon trusting files, folders or an environment that the relay account
could change.

**Rule.** Your answer 3: A.
- The reviewer reads the earlier phases' `specs/*/reviews/pal-review-plan-*.md` and
  `specs/*/reviews/owner-*.md` (the last 5 phases that have them) and collects their major and
  critical findings.
- It adds the harness's fixed list, drawn from phase 011:
  1. code that runs as another account or elevated, and anything the trusted side reads, runs, writes
     or deletes in a place the less-trusted side can change (config, hooks, junctions, output files);
  2. a child process's environment copied from the owner's (profile paths, secrets);
  3. a key, secret, token or invitation handoff (who receives it, how the sender checks them);
  4. absolute security wording with nothing enforcing it (change 10);
  5. a contract row or appendix behaviour with no task.
- Before the other checks, it checks each item that fits this plan's kind of work. The report gets an
  **Earlier majors** table: the source (phase, report, finding) or `harness list`, the risk in one
  line, whether it applies and why, and where the plan covers it (a task) or the finding it raised.
- An item that applies and is not covered is a finding at its original severity.

### 4. Windows-security tests as the runner's account, before the PR [22] (`skills/phase/references/plan.md`, `skills/phase/references/build.md`, `skills/quick-fix/SKILL.md`, `agents/review-plan.md`, `practices/devops_cicd.md`, `practices/testing.md`)

**Problem.** Phase 011's Windows-security tests were never run as a non-interactive standard user
before the PR. Four failed only on the runner and cost two extra pushes.

**Rule.** Your answer 4: A.
- A phase or quick fix **touches Windows security** when it adds or changes code or tests that use
  ACLs, accounts, tokens or privileges, window stations or desktops, services or named pipes. The
  plan's summary says so, and its last task before the PR is the session-0 run. The plan reviewer
  checks both.
- The project's `CLAUDE.md` may name the command in one line, `Session-0 tests: <command>`. The
  command runs those tests as the self-hosted runner's account in session 0 and returns their exit
  code.
- Before opening the PR, the session runs it once on the branch head and saves the output as
  `specs/NNN-slug/reviews/session0-YYYY-MM-DD-HHmm.md`. Red → fix it test first, then run it again.
  It gets 3 rounds, then the build is stuck (build.md section 5). It runs again only when a later fix
  changes that code or those tests.
- With no command named: if `ci.yml` has `workflow_dispatch:` and the Windows job runs on a
  self-hosted runner, push the branch, `gh workflow run ci.yml -R <owner/repo> --ref <branch>`, and
  watch the run in the foreground (change 2). In Pal Center, CI's fingerprint gate then skips the same
  job on the PR. Otherwise write `session-0 run: not available (<reason>)` in the log and the PR
  body.
- `devops_cicd.md`: a self-hosted runner costs no minutes, so its Windows jobs may also run on
  `workflow_dispatch` (the 2x rule is about GitHub's runners).

*Pal Center product capture:* a `Session-0 tests:` command for Pal Center (a scheduled task as
`ghrunner`, set up once by you in an admin PowerShell) and `workflow_dispatch:` in its `ci.yml`.

### 5. A Trust boundaries section in the spec [23] (`templates/spec.md`, `skills/phase/references/spec.md`, `agents/review-plan.md`, `agents/review-security.md`)

**Problem.** In phase 011, the critical that became decision 33 (Trust windows ran as `palrelay` on
your desktop, loading config the relay could write) surfaced only at the final review. The spec,
several tasks and a re-review were redone after the build.

**Rule.** Your answer 5: A.
- A spec needs a **Trust boundaries** section when code runs as another account or elevated, or reads
  a file, config, environment, pipe or registry value that another account or a less-trusted process
  can write. Otherwise the section is deleted, like Contract.
- A table with one row per input that crosses the boundary: the input, who can write it, who reads or
  runs it and as which account, the session or desktop, what stops misuse, and what it does not stop.
- Under it, one line per process that runs as another account or elevated: who starts it, which
  binary (and who can write that path), and where its environment comes from.
- Codex's spec review reads it as part of the spec. The plan reviewer checks that a task builds and
  tests each "what stops misuse" cell. The security reviewer checks the code against it.

### 6. A short path for a mid-build request [24] (`skills/phase/references/build.md`)

**Problem.** In phase 010 you asked for AltXezio version info mid-build (decision 22). It became Task
14 with no path in the skill.

**Rule.** A new **An owner request during the build** step in build.md section 4 (your answer 6):
- **It fits** when it is at most one task (about 2 hours), stays in repos the phase already touches,
  adds no feature and makes no breaking API change. Then:
  1. append it to `doc/decisions.md` (`N. YYYY-MM-DD (phase NNN): mid-build request: <request> →
     added as Task K`);
  2. add Task K to `plan.md` under **Added during build**, with the five fields every task names; add
     1 to `tasks.total`; write the log entry;
  3. if you will see the change, add a test step to the feature's test script in the spec and
     `doc/features.yaml` (under `no-owner-test`, a What to expect now line);
  4. build it like any task. It gets the per-task review in a larger build and the whole-branch review.
     There is no `pal-review-plan` re-run;
  5. the sign-off PR lists it under Calls I made with its decision number.
- **It does not fit:** the session tells you in one line and adds it to `doc/features.yaml` as `todo`
  with its why and use case. `/pm` puts it on the board.

### 7. A Defender block on a Pal Center CLI [25] (`skills/phase/SKILL.md`)

**Problem.** In phase 010, Windows Defender blocked `pal-work.exe` (heuristic Bearfoos.A!ml). Work
state was not reported until you added an exclusion.

**Rule.** Your answer 7. The phase skill's **Until Pal Center and CI catch up** table gets a row:
a Pal Center CLI that Defender blocks ("the file contains a virus or potentially unwanted software",
or the `.exe` missing after quarantine) is treated as exit 5 for that CLI. The session tells you once,
in the session and in the next owner-stop message, with the command for an admin PowerShell:
`Add-MpPreference -ExclusionPath "<the exact .exe path>"`. It never excludes a folder or a process.

*Pal Center product capture:* a Setup step that excludes the exact paths of the Pal Center CLIs, the
same line in the new-PC checklist (`doc/owner-checklist-w0.md`), each release's binaries sent to
Microsoft as a false positive, and code signing to weigh later (it costs money).

### 8. Local Go tests with less memory [26] (`practices/testing.md`, `skills/phase/references/build.md`)

**Problem.** In phase 010, subagents' `make test` runs were killed by low memory, and the
coordinator ran `go test -p 1` itself.

**Rule.** Your answer 8: A.
- Every local Go test run, by a session or a subagent, sets `GOFLAGS=-p=1` and `GOMEMLIMIT=2GiB` in
  the command's environment (`GOFLAGS=-p=1 GOMEMLIMIT=2GiB make test`), so `make test` follows them
  with no Makefile change. CI never sets them.
- The implementer brief in build.md says so.

### 9. Full checks after every fix round [27] (`skills/phase/references/review.md`, `skills/phase/references/build.md`, `skills/phase/references/staging-test.md`, `skills/quick-fix/SKILL.md`)

**Problem.** In phase 010, a typing error from review fix round 3 was found only by CI. The round
re-ran Go tests and Vitest on one file, not `npm run typecheck`.

**Rule.** Your answer 9.
- A fix round in the whole-branch review, a quick fix or a staging-test fix counts as done only when
  the repo's full lint, typecheck and test commands (`workflow.md`, **Check before every push**) pass
  in every repo it changed. Each result is read from its own exit code. A single-file or
  single-package run does not count.
- A per-task fix round in a larger build runs the task's prove-it commands plus the repo-wide lint and
  typecheck. The full tests run once, at the end of the build, before the PR.

### 10. No absolute security wording without its enforcement [28] (`skills/phase/references/spec.md`, `agents/review-plan.md`, `agents/review-security.md`)

**Problem.** In phase 010, the spec said the deny list "cannot" be overridden. Codex's code review
rated it critical, since it is not an OS sandbox. That cost an owner stop at the end of review, a new
feature (F-017), and the relay shipped off by default.

**Rule.** Your answer 10.
- While drafting, each claim that a security limit holds ("cannot", "never", "guarantees",
  "ensures", "prevents", "only X can") names what enforces it (an OS ACL, a check in code with its
  test, a token's scope) and what it does not cover. A limit kept only by convention or a deny list is
  written as what it reduces ("blocks the listed commands").
- The plan reviewer flags any such claim left in the spec: minor when an enforcement is named but the
  wording claims more, major when nothing enforces it.
- The security reviewer does the same for owner guides, UI text and comments in the code.

*Pal Center product capture:* Codex's spec-review prompt (`review_prompt.go`, kind `doc`) flags the
same wording.
