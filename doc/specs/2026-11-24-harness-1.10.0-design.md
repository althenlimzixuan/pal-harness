# pal-harness 1.10.0: filled QA screens, cheaper task reviews, and phase 022's and 023's lessons

**Status:** Draft, after "accept all" to the 7 questions on 2026-11-24.
**Source:** 10 harness notes raised in Pal Center (ai-workshop#58 to #67), from Pal Center phase
022's and 023's retros, worked in session HARNESS-work-VEK8MY.
**Delivers:** pal-harness 1.10.0:
- two new commands, `pal-harness minors` and `pal-harness merge-check`;
- a fix to `pal-harness spec new`;
- rule text for the rest.

It is a minor version because of the new commands (answer 1). No state field changes, so Pal Center's
reader is not affected. The `upgrade` command and the automatic re-pin move to 1.11.0.

## Summary for the owner

1. **QA shows filled screens.** The spec lists the sample data each changed screen needs, the plan
   adds whatever the project's QA data lacks, and the QA pass screenshots the screens filled.
2. **Fewer task-review rounds spent on process.** New tests are matched to their failing run by
   name before any code is reviewed. The plan can mark guard tests that pass on purpose. The
   reviewer breaks the code once per new test to prove the test can fail.
3. **Deferred minors are tagged when they are found**, and `pal-harness minors` lists them, so the
   end of the build stops re-reading the whole ledger.
4. **The plan review looks every command and path up** in the repo, and checks that code for one OS
   has a check for that OS in the plan.
5. **A fix stays inside its finding.** When a fix would change what you see beyond the finding, the
   fixer stops and it becomes a question for you, not a quiet change.
6. **Conflicts show up before CI.** `pal-harness merge-check` tries the merge with `origin/dev` at
   the start of the review stage and before each PR opens.
7. **Done work drops out of a fix pack.** Before backlog issues become a phase, each is checked
   against the feature list, merged PRs and closed issues, and done ones are closed with the link.
8. **`spec new` starts from `origin/dev`**, never from a stale local `dev`.

## Changes

Issue numbers in brackets are in ai-workshop. Everything ships in one PR into `dev`.

### A. QA seeds [#58] (`templates/spec.md`, `skills/phase/references/spec.md`, `skills/phase/references/plan.md`, `skills/phase/references/qa.md`, `agents/review-plan.md`)

**Problem.** Phase 022's QA environment had no data for the changed screens (the Exit all dialog,
the Auto review switches, the notices), so they were reviewed from code and a few screenshots.

**Rule.** Answer 4. Nothing new in `project.yaml`.
1. **The spec.** The UX outline ends with a **QA seeds** line: the records each changed screen needs
   to look filled (for example "3 audit lines, a paused project, a held decision"), or `none`.
2. **The plan.** A seed the project's QA sample data does not hold yet gets a task that adds it there
   (in Pal Center, the `qaseed` fixture `daemon/tests/fixtures/qa-sample.json`), with a test that the
   seeder loads it. The task lists the file it changes.
3. **The plan review.** Check 13 (**Data sources**) also covers the seeds: every QA seed exists in
   the QA data (the reviewer finds it with Grep) or has a task. A seed in neither is a major finding.
4. **The QA pass.** Each changed screen is screenshotted in its seeded state, and the `summary.md`
   row names the seed it showed. A screen that came up empty when its seed exists is a failed step.

### B. RED by test name, and guard tests [#59] (`skills/phase/references/subagents.md`, `skills/phase/references/build.md`, `templates/plan.md`)

**Problem.** In phase 022, task reviews sent work back three times because RED evidence was missing
(Task 3, Task 5, and a guard test that needed an exemption ruling). Each time a review round went on
process, not code.

**Rule.** Answer 3.
1. **Before the review.** The controller lists every new test by name from the task's diff (Go
   `func Test…`, Jest `it(`/`test(`, Rust `#[test] fn …`, Playwright `test(`) and finds a RED line
   for each name in the report. A name with no RED line goes back to the implementer **before** the
   task reviewer is dispatched. The task reviewer's check 1 repeats the match by name.
2. **Guard tests.** The plan's task block gains an optional **Guard tests:** line: tests that pin
   behaviour that is already there, so they pass on their first run, each with its reason. A guard
   test's RED is a mutation run (C3 below): break the code it guards, run it, see it fail, restore.
   A guard test listed in the plan needs no exemption ruling.
3. **A late RED.** A test whose RED was missing can only show RED by a mutation run now that the
   code exists. The implementer does that run and logs `RED by mutation: <test>`. It is not a fix
   round, and it doesn't count as a review round. A test that stays green under the mutation is
   rewritten, which is a fix round.
4. An inline build does the same: keep each test's RED by name, and a guard test's mutation run.

### C. Mutation check in the task review [#66] (`skills/phase/references/subagents.md` section 3)

**Problem.** Phase 022 Task 3's review broke the code by hand and found a test that tested
nothing. Phase 023 Task 1 had a collision test that could not fail.

**Rule.** Answer 3.
1. The task reviewer's checks gain **Mutation check**: for each new test (at most 5 per task,
   choosing the tests of the task's main behaviours), make one small break in the code it covers
   (flip a condition, drop a call, return early), run that test, and confirm that it fails.
2. Restore every file you changed (`git restore -- <files>`), then check `git status --porcelain`
   shows nothing the review didn't start with.
3. A test that stays green is an Important finding: "`<test>` passes with `<break>`".
4. The reviewer names each break and its result in its report, so the controller can see it ran.

### D. Deferred minors tagged at triage, and `pal-harness minors` [#60] (`skills/phase/references/subagents.md`, `skills/phase/references/build.md` section 6, `agents/review-code.md` check 8, new command)

**Problem.** Phase 022 parked about 25 minors in the ledger and marked only a few for the final wave.
The end of the build had to triage them all again, by hand (as in phase 021).

**Rule.** Answer 2.
1. **Tag at triage.** When a task review's minors are triaged, the controller writes each deferred
   one into sdd's ledger with a tag:

   `Task 3: minor (deferred) [carry]: Cancel label reads "Close"`

   | Tag | Where it goes |
   |---|---|
   | `carry` | the next task's **Carry-over** list (1.9.0); the last task's go to the final fixer |
   | `final` | the one fixer before the whole-branch review |
   | `later` | a `doc/later.md` line |
   | `issue` | a real bug: a backlog issue |
   | `fixed` | written over the tag once it's fixed (`[fixed]`) |

   sdd's own `Task N: parked — … — Ruling: …` lines are left as they are and listed as `parked`.
2. **`pal-harness minors <ledger> [--tag <tag>] [--task <N>]`** reads the ledger and prints the
   minors grouped by tag, `carry` first, then `final`, `later`, `issue`, `parked`, `untagged`, then
   `fixed` as a count only:

   ```
   carry (2)
     Task 3: Cancel label reads "Close"
     Task 3: stale comment in tray.rs
   later (1)
     Task 2: log line could name the port
   untagged (1)
     Task 5: minor (deferred): no notice while Stop all runs
   ```

   Exit 0 when every minor is tagged, 1 when one is untagged or has an unknown tag, and 2 when the
   file can't be read or an argument is wrong. `--task` and `--tag` filter the list. The controller
   builds task K+1's Carry-over list with `--task K --tag carry`.
3. **The end of the build.** `build.md` section 6 **Deferred minors** runs `pal-harness minors` in
   place of re-reading the ledger:
   - untagged lines are tagged first;
   - `carry` and `final` lines go to the one fixer;
   - `later` lines become `doc/later.md` lines;
   - `issue` lines become backlog issues.

   The log line gives the counts per tag.
4. `pal-review-code` check 8 reads the same list: each `later` or `issue` minor is in `doc/later.md`
   or a backlog issue.

### E. Plan review looks up every command and path [#61] (`agents/review-plan.md` new check 19, `skills/phase/references/plan.md`)

**Problem.** Phase 022's plan review found fixture folders that don't exist, test files with the
wrong names, and generator steps missing from a task. Each one was a lookup that nobody had done.

**Rule.**
1. **The plan writer** looks up, once and before the review, every command and path a task names:
   - each existing file or folder;
   - the folder and naming of each new file (a fixture beside the real fixtures);
   - each make target, npm script and generator flag;
   - each file the spec names as the origin of a behaviour.
2. **Check 19, Commands and paths.** The reviewer repeats the lookups with Glob and Grep: paths in
   the tree, make targets in the `Makefile`, scripts in `package.json`, generator flags in the
   generator's config or source. A path or command that isn't there is a minor finding, or a major
   one when the task's design depends on it (the wrong file to change, a step that can't run).

### F. A fix stays inside its finding [#62] (`skills/phase/references/review.md` section 4, `skills/phase/references/subagents.md`)

**Problem.** In phase 022, review fix item J changed what the owner sees: `ok?!` stopped approving.
It was reverted in round 2. The fix prompt said "fix the finding", but nothing stopped the fixer from
changing behaviour the owner can reach.

**Rule.** Answer 7.
1. **The fixer's brief** (the review fix rounds, a task's fix rounds and the final fixer) says that a
   fix may change behaviour the owner can see or reach only as far as its finding says. That covers
   text, controls, defaults, and what an answer or a click does.
2. If the finding can't be fixed without more, the fixer leaves that part alone and reports it under
   **New question**: what it would change, and why the finding needs it.
3. **The session** handles the question:
   - when a findings stop is already coming, the question joins it;
   - otherwise it becomes a backlog issue, with a recommended answer and
     `Why: a fix needs an owner-facing change`, and is listed in the sign-off PR's review table.

   The phase goes on either way. The finding is recorded as partly fixed, with the issue link.
4. The re-check after a fix round also compares the fix with its finding. Behaviour the owner sees
   that changed beyond the finding is a finding of its own.

### G. Merge check before CI [#63] (new command, `skills/phase/references/review.md` section 1, `skills/phase/references/build.md` section 6, `skills/quick-fix/SKILL.md`)

**Problem.** Phase 022's PR #192 conflicted with `dev` on `doc/decisions.md`, because a bookkeeping
PR had merged decision 105 during the build. CI didn't run, and the conflict was only found at the
review stage.

**Rule.** This is a command, not a git one-liner as I said earlier. `git merge-tree --write-tree`
needs git 2.38, and this PC has 2.34.
1. **`pal-harness merge-check [--base origin/dev] [dir]`** fetches the base's branch, then tries the
   merge of `HEAD` with the base in a throwaway worktree in the temp folder. The session's own tree,
   index and branch are never touched, and the throwaway worktree is always removed.
   - Clean: `merge-check: clean against origin/dev`, exit 0.
   - Conflict: `merge-check: conflicts with origin/dev:`, then one conflicted path per line, exit 1.
   - The fetch fails, or the folder isn't a git repo: exit 2, with the reason.
2. **When.** In every repo of the set:
   - at the start of the review stage, before the reviewers;
   - before each PR into `dev` opens (build section 6 step 3, and the quick fix's PR).

   On a conflict, merge `origin/dev` into the branch now. A bookkeeping file (`doc/decisions.md`,
   `doc/later.md`, `doc/features.yaml`) keeps both sides' entries. Then run the full check again and
   push. It is not a fix round.

### H. Checks for other operating systems in the plan [#64] (`templates/plan.md`, `skills/phase/references/plan.md`, `skills/phase/references/linux-check.md`, `agents/review-plan.md` check 20)

**Problem.** In phase 022, Linux-only Rust code couldn't be compiled on the Windows PC. CI's Linux
clippy found an unused helper meant only for Windows, which cost one red run and a fix commit
(539bec2).

**Rule.**
1. **The plan.** A task that touches code for one OS (a Go file with an OS suffix or build tag, Rust
   under `cfg(target_os …)`, `cfg(unix)` or `cfg(windows)`) adds to its **Prove it** the check for
   each other OS that code builds on:
   - **Go:** `GOOS=linux go vet ./...` and `GOOS=darwin go vet ./...`. With golangci-lint:
     `GOOS=linux golangci-lint run ./...`.
   - **Rust, pure crates:** `rustup target add x86_64-unknown-linux-gnu`, then
     `cargo clippy --target x86_64-unknown-linux-gnu --all-targets -- -D warnings`. For macOS, the
     same with `aarch64-apple-darwin`.
   - **Rust with system libraries** (Tauri, GTK, WebKit, anything whose build script needs the
     target's libraries): the Docker run in `linux-check.md` for Linux. For macOS there is no local
     proof: the task says `macOS proof: CI's macOS job`.
2. **`linux-check.md`** gains the `cargo clippy --target` step under **Cheap first**, and a macOS
   line.
3. **Check 20, Other operating systems.** A task that touches code for one OS and has no check for
   the other OSes it builds on is a minor finding.

### I. Done work drops out before a fix pack [#65] (`skills/pm/SKILL.md` **Bundle and vehicle**, `skills/phase/references/spec.md`)

**Problem.** Phase 022 existed because 41 notes sat unfiled in the Inbox. About a dozen were already
done elsewhere and had to be found and closed by hand.

**Rule.** Answer 5.
1. Before a bundle that holds backlog issues is proposed, and again when the spec lists them, check
   each issue against three sources:
   - `doc/features.yaml`: a `done` feature that covers it;
   - merged PRs: `gh pr list -R <owner/repo> --state merged --search "<key words>"`;
   - closed issues: `gh issue list -R <owner/repo> --state closed --search "<key words>"`.
2. A done one is closed with a comment that links the PR, feature or issue that did it
   (`gh issue close <n> -R <owner/repo> --comment "Done in <link>"`), and its card goes to `Done`.
   The bundle and the spec hold only open work, and the spec's summary gives the count closed.
3. Pal Center's own Inbox triage gets the same check through Pal Center F-036, outside this release.

### J. `spec new` branches from `origin/dev` [#67] (`cmd/pal-harness`)

**Problem.** In phase 023, `pal-harness spec new` branched from a stale local `dev`, and the session
had to run `git reset --keep origin/dev`.

**Rule.** Answer 6.
1. When the repo has an `origin` remote, `spec new`:
   1. runs `git fetch origin dev`;
   2. stops with a message when the fetch fails, when there is no `origin/dev`, or when local `dev`
      has commits that aren't on `origin/dev`. The message gives the count and says to push or drop
      them;
   3. otherwise creates `docs/NNN-slug` from `origin/dev` with `--no-track`, so a push never goes to
      `dev`.
2. With no `origin` remote, it uses local `dev`, as today.
3. Numbering is unchanged.

## Release

- **Version 1.10.0:**
  - `harness.go`, `.claude-plugin/plugin.json` and a `CHANGELOG.md` section;
  - the README command table (`minors`, `merge-check`, the `spec new` change);
  - `templates/ci.yml` names `@v1.10.0`.
- **Tests:**
  - `TestHarness1100Rules` pins the new rule phrases;
  - `TestContentComplete` keeps the line caps. `spec.md` (150 of 150) and `build.md` (149 of 150)
    are edited by rewriting text in place;
  - `minors`: grouping, the `--tag` and `--task` filters, untagged and unknown tags (exit 1), a
    missing file (exit 2), `parked` and `fixed` lines;
  - `merge-check`: clean (exit 0), a conflict that lists the path (exit 1), no repo or a failed fetch
    (exit 2). Each test also checks that the caller's tree, branch and worktree list are unchanged;
  - `spec new`: branches from `origin/dev` when local `dev` is behind; stops when local `dev` is
    ahead; stops when the fetch fails; sets no upstream; with no remote, uses local `dev`.
- **One PR into `dev`** with one Closes line per note (#58 to #67). It merges on green CI. Then one
  `[HUMAN GATE]` `dev` → `staging` PR, which you merge. Then `staging` → `main`, the `v1.10.0` tag
  on the merge commit, and the CHANGELOG entry. Codex review is skipped (`pal-review` knows only
  workspace projects), and the PR says so.
