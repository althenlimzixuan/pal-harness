# pal-harness 1.11.1: Pal Center phases 026 and 027's lessons, and a readable unknown mode

**Status:** Approved by the owner on 2026-11-24, after "accept" to the 7 questions the same day.
**Source:** 10 harness notes (ai-workshop#78 to #87): one from LFPV, nine from Pal Center phases 026
and 027's retros. Worked in session HARNESS-work-GHSKM7.
**Delivers:** pal-harness 1.11.1, rule text only: no new command, no state field (answer 1). The
`upgrade` command and the automatic re-pin stay in 1.12.0.

## Summary for the owner

1. **An unknown Company mode is said once.** When `pal-work mode` fails (exit 4 or 5), the session
   logs one line with the reason and tells you once, in the first owner stop. A Pal Center issue
   asks `pal-work` to print the real reason instead of "internal error".
2. **Findings pages show each option's side effects.** A new owner-stop template makes an option
   that widens a failure rule say what else it stops or hides, before you pick it.
3. **Wording isn't "major".** A Codex spec finding that changes only wording counts as minor at most.
   A Pal Center issue puts the rule in Codex's prompt itself.
4. **Errors are traced task by task.** The per-task reviewer traces each documented status code of a
   new route to the code that returns it and to a test that reaches it.
5. **Layouts are seen in the task.** A UI task whose spec gives pixel sizes takes one screenshot with
   sample data before it is done.
6. **Saves stay per item.** A screen with several save buttons never lets one save overwrite another
   item's value. The brief says so and the task reviewer checks it.
7. **Tests by name.** The plan's task block asks for the failing test names, never a count.
8. **No more cut test runs in subagents.** A subagent runs only its own Go packages. The session runs
   the full suite in package groups.
9. **One mock at a time works.** `go_api.md` gives a command that works with `all: true`.
10. **A missing reviewer type has a named fallback.** After a restart, the session uses a
    general-purpose agent told to follow the reviewer's file, and logs it.

## Changes

Issue numbers in brackets are in ai-workshop. Everything ships in one PR into `dev`. `SKILL.md`
(250 of 250 lines), `review.md` and `build.md` (150 of 150 each) are edited by rewriting text in
place only.

### A. An unknown mode, said once [#78] (`skills/phase/references/company-mode.md` section 1)

**Problem.** In LFPV, `pal-work mode --project lfpv` returned `internal error` with exit 4. The
reference names only exit 5 as an unknown mode, and the session noted the fallback at every stop.
The command answers normally today (exit 0), so the failure was intermittent.

**Rule.** Answer 2.
1. Exit 4 (failed), exit 5 (not running), no `Work CLI:` line or a `Pal Center version:` older than
   0.21.0: the mode is unknown, and every stop waits for the owner.
2. **Said once.** The session writes one log line at the start, with the CLI's own message:
   `mode: unknown (exit 4: <its message>); every stop waits for the owner`. The first owner-stop
   message carries the same line. Later stops don't repeat it.
3. **One retry.** On exit 4 the session runs `mode` once more before it decides. A second exit 4 is
   unknown.
4. **Pal Center issue:** exit 4 from `pal-work mode` prints the failing step and its cause (which
   project, which file or call), never a bare `internal error`.

### B. The findings page: each option's blast radius [#86] (new `templates/owner-stop.md`, `skills/phase/SKILL.md` **Owner stops**, `skills/phase/references/review.md` section 3)

**Problem.** In Pal Center phase 026, decision 116 ("fail the whole Feedback board read on any
unreadable card") silently stopped every new feedback line. Narrowing it took a review round, a
63-minute owner stop and a fix round (decision 117).

**Rule.** Answer 4.
1. **The template.** A new `templates/owner-stop.md` for findings and questions pages:
   - the problem;
   - what was tried;
   - numbered options with a recommended one.

   Each option has three lines:
   - `Does:`;
   - `Also stops or hides:`, required when the option widens a failure rule (makes more things
     fail, stop, skip or disappear): every other flow, list or screen it would also stop or hide, or
     `nothing else`;
   - `Cost:`.
2. **Pointers.** SKILL.md (**Owner stops**, the sentence on findings and question pages) and
   `review.md` section 3 name the template. Both are rewritten in place, with no added lines.
3. The recommended option is checked the same way. An option whose blast radius is unknown says
   `unknown: <what was not checked>`, and is never the recommended one.

### C. Codex: wording is minor at most [#83] (`skills/phase/references/spec.md` section 4 step 3)

**Problem.** In Pal Center phase 027, Codex's spec review read "major" for one sentence that changed
nothing about what gets built.

**Rule.** Answer 3.
1. A Codex doc finding is **wording-only** when fixing it changes no behaviour, no contract, no data
   and no test script. That covers what gets built, its tests and the owner's test steps.
2. The session regrades a wording-only major or critical to minor, fixes it in the spec, and lists it
   in Calls I made: `Codex doc <id>: wording only, rated minor (<one line>)`. A finding that changes
   anything else keeps its level.
3. **Pal Center issue:** the `doc` prompt in `review_prompt.go` says wording-only findings are minor
   at most, so the verdict doesn't read major for a sentence.

### D. The task reviewer traces each documented status code [#79] (`skills/phase/references/subagents.md` section 3)

**Problem.** In Pal Center phase 027, a documented 503 could never be returned. Only the
whole-branch contract reviewer found it, in round 1.

**Rule.** Answer 7. A new task reviewer check: for each route the task adds or changes, it lists every status
code the contract (`openapi.yaml`, `doc/API.md`) documents for it. For each code, it names the line
that returns it and a test that reaches it. A documented code that no path returns is a major
finding, and so is one with no test. Small inline phases and quick fixes keep the whole-branch
`pal-review-contract`.

### E. Red evidence by name, in the plan [#80] (`templates/plan.md` **Test first:**, `skills/phase/references/plan.md` section 1 item 2)

**Problem.** Task 4's red-test evidence in phase 027 was a count ("7 failed"). It was accepted on
the controller's judgement.

**Rule.** The task block's **Test first:** line adds: "RED evidence: the failing test names, from
the run's own output (the command and the lines that name each test), never a count." `plan.md`
item 2.2 says the same.

### F. Pixel values rendered in the task [#84] (`templates/plan.md` new **Render check:**, `skills/phase/references/plan.md` section 1, `skills/phase/references/subagents.md` section 3)

**Problem.** In phase 027, a spec's grid size and row height overlapped on screen. It showed only in
the whole-branch review, which took 3 rounds.

**Rule.** Answer 5.
1. A UI task whose spec gives pixel values (a grid size, a row height, a width) has a
   **Render check:** field with:
   - the values;
   - the sample data that fills them (the longest real label, the most rows);
   - the screenshot path, `specs/NNN-slug/screens/task-K-<name>.png`.
2. Before the task is done, the screenshot is taken once with that data (the project's
   `screens.spec.ts` or QA command, or the app run by hand), committed, and looked at. Nothing
   overlaps, is clipped or is cut off.
3. The task reviewer (in an inline build, the session) opens the screenshot. A missing screenshot,
   or one that shows overlap, is a finding.

### G. Saves are per item [#85] (`skills/phase/references/subagents.md` sections 1 and 3, `templates/plan.md`)

**Problem.** In phase 027, Task 6 had several independent switches and forms. One stale save
overwrote another item's value, which cost a fix round.

**Rule.**
1. **The brief** of a UI task with several independent save buttons (switches, forms) says: each
   save sends only its own item. A save that answers after a newer one never overwrites another
   item's value, or a newer value of its own item.
2. **The plan.** Such a task's **Code:** line says "saves per item".
3. **The task reviewer** checks it, with a test: two items saved close together, the first answer
   arriving last, and both values right afterwards.

### H. Subagents run only their own Go packages [#82] (`skills/phase/references/subagents.md` section 1, `practices/testing.md` Go-Specific)

**Problem.** In phase 027, subagents' full Go runs were cut by low memory or the 10-minute tool
limit, and the controller re-ran them.

**Rule.**
1. **The brief:** a subagent runs only the Go packages its task changed, plus the packages that
   import them when the task changed an exported name (`go test <its packages>`, with
   `GOFLAGS=-p=1 GOMEMLIMIT=2GiB`). It never runs `./...` or `make test`.
2. **The controller** runs the full suite, after `pal-harness mem`, in package groups with
   `GOFLAGS=-p=1`, each in the foreground with a Bash timeout of 600000 ms. It runs it before the
   whole-branch review (`build.md` section 6 step 1) and for a fix round's check. A group is the
   same one `devops_cicd.md` step 4 uses for a cut run. A group cut by low memory is re-run alone.
   A group that hits the 10-minute limit is split in two.

### I. One mock with `all: true` [#81] (`practices/go_api.md` **Mocks.**, `practices/devops_cicd.md` step 4)

**Problem.** `mockery --name <Interface>` stops with `Specify --name or --all, but not both` when
`.mockery.yaml` has `all: true`.

**Rule.** Answer 6. The per-interface command becomes:

```
go run github.com/vektra/mockery/v2@v2.53.7 --name <Interface> --all=false --dir <its package folder> --output mocks
```

`--all=false` overrides the file, and `--dir` limits the search to that package. Verified on
2026-11-24 with v2.53.7: it writes only `mocks/<Interface>.go`, package `mocks`. No Makefile target
is added.

### J. Reviewer agent types missing [#87] (`skills/phase/references/subagents.md` new section 5, `skills/phase/references/review.md` section 2 item 2)

**Problem.** In phase 026, after a session restart, the `pal-review-*` agent types were not
available. The session improvised.

**Rule.**
1. When a `pal-review-*` (or `pal-retro`) agent type can't be dispatched, the session dispatches a
   general-purpose agent whose brief:
   - opens with "You are `<name>`. Follow `<set>/.pal-harness/agents/<file>.md` exactly: it is your
     whole definition, its checks and its report format";
   - adds the inputs and the report path the agent would have had.

   The agent file's `model:` is passed as the model.
2. It is logged once per session: `agent fallback: general-purpose for <names> (<why>)`. The report
   counts as that reviewer's.
3. `review.md` section 2 item 2 points to it, rewritten in place.

## What to expect now

Try it in **Pal Center** (`pc`), after its re-pin to 1.11.1. The re-pin is a separate step you
choose, and this release doesn't do it. LFPV shows A and C as well. 1.11.1 adds no state field, so
the installed Pal Center reads 1.11.1 phase state as it reads 1.11.0.

| # | What you'll see | Where |
|---|---|---|
| 1 | When `pal-work mode` fails, one log line `mode: unknown (exit 4: …)` and one mention in the first stop, not one at every stop | LFPV or PC, the next time `mode` fails |
| 2 | A findings or questions page whose options each say `Also stops or hides:` | PC's next findings stop |
| 3 | A wording-only Codex spec finding listed in Calls I made as `rated minor`, not as a major question | PC's next spec |
| 4 | The per-task review report names each documented status code with its line and test | PC's next phase that adds a route |
| 5 | `screens/task-K-*.png` committed by a UI task with pixel values | PC's next phase with a sized layout |
| 6 | A "saves per item" line in a task with several save buttons, and its test | PC's next settings-style screen |
| 7 | Plan tasks' Test first line asks for RED names; reports list names, not counts | PC's next plan |
| 8 | Subagent reports show package-scoped Go runs; the full suite runs in groups by the session | PC's next larger build |
| 9 | A one-interface mock made without a full `make mock` | PC's next Go task that changes an interface |
| 10 | `agent fallback: general-purpose for …` in the log after a restart, with the review going on | Any phase resumed after a restart |

## Release

- **Version 1.11.1:**
  - `harness.go`, `.claude-plugin/plugin.json` and a `CHANGELOG.md` section;
  - `templates/ci.yml` names `@v1.11.1`.
- **Tests:**
  - `TestHarness1111Rules` pins the new rule phrases;
  - `TestContentComplete` keeps the line caps and lists the new template.
- **One PR into `dev`**, with one Closes line per note (#78 to #87). It merges on green CI. Then:
  1. one `[HUMAN GATE]` `dev` → `staging` PR, which you merge;
  2. `staging` → `main`;
  3. the `v1.11.1` tag on the merge commit, and the CHANGELOG entry.

  Codex review is skipped (`pal-review` knows only workspace projects), and the PR says so.
- **Follow-up issues in Pal Center** (filed when the PR opens):
  - `pal-work mode` exit 4 prints its real reason (A4);
  - the Codex `doc` prompt rates wording-only findings minor at most (C3).
