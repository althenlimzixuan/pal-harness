# pal-harness 1.8.0: Pal Center's new flows, steadier builds and the 61 open notes

**Status:** Approved by the owner on 2026-11-19, after "accept all" to the 17 questions the same day.
**Source:** the 61 harness notes left in Pal Center's inbox after the 2026-11-19 clean-up (Pal Center
phases 005 to 019, LFPV phases 006 to 011), worked as one release (option A) in session
HARNESS-work-9XPS5V. Note #64 stays open (answer 16).
**Delivers:** pal-harness 1.8.0:
- five new reference files and one new template;
- one new command (`utf8`);
- two schema additions (`check:` in feature results, and `qa:` with `qa_command`);
- one new flow override (`uat-queue`);
- rule text for the rest.

It is a minor version. The `upgrade` command and the automatic re-pin move to 1.9.0.

## Summary for the owner

1. **Sessions follow Company mode.** Every pickup, phase and quick-fix session checks
   `pal-work mode` first. At a spec-review or findings stop with Company mode on, the session parks on
   `wait-decision` and acts on what it returns. A question about money, a password or key, or
   anything public is always held for you.
2. **Pickup runs chores first and says why it skipped a card.** It follows Pal Center's order: due
   chores, then approved cards, then Pal's pick, then safe backlog items. A session suggests a chore
   card and creates it only after your yes.
3. **A QA pass before your staging test.** A project that names a QA command in `project.yaml` gets
   a session-run check of every What to expect now line, with screenshots, before you are asked to
   test.
4. **The UAT queue (off until you switch it on).** Under `uat-queue`, up to 3 phases can wait on
   staging for one combined test, and ship promotes them together.
5. **CI waits stop costing runs.** Nothing is pushed to a PR's branch while its CI runs. The watch
   runs under `timeout 520`, so Claude Code cannot move it to the background. Lint, mocks and Jest
   check memory first and have a smaller retry when memory runs out.
6. **Subagents are kept on a shorter leash.** A repeating implementer is stopped. A stale reply is
   sent back. Each task brief carries the findings that keep recurring, and each task review checks
   the wording you will read.
7. **Plans and specs catch more before the build.** Plan review stops after a round with only minor
   findings and cross-checks file lists. Delete tasks test links and junctions. Mobile phases bump
   the app version, and native dependency changes get a version check. The spec covers new requests,
   live changes, hardware you can't reach and the store identity. Plain English is the rule
   everywhere.
8. **Reviews ask the questions that cost fix rounds.** These are client timeouts against server
   budgets, error mapping, concurrency and lifecycle, kill switches, failure paths, the retry after a
   fix, and fixtures taken from real responses.
9. **Your staging tests are smoother.** There's a seed for the two test roles, a Docker check in
   pre-flight and an app-data reset. Steps are worded so they can't be misread, and destructive
   steps are split out. A split plan is repeated back to you before anything acts on it.
10. **Release steps are written down before ship.** There's an Android release runbook, the
    commands only you can run are listed in the plan, the Vercel and Cloud Run rules are set, every
    runbook is dry-read against your real files, and there's a self-hosted runner rule.
11. **Checks the harness enforces:** named extra checks in feature results; a hint listing the
    allowed fields; a gate step that rejects non-UTF-8 text; and a speed check that ignores
    sub-2 ms noise.

### Part A: Pal Center's new flows

#### A1. Company mode and the veto window [59, 95] (new `skills/phase/references/company-mode.md`; `skills/phase/SKILL.md`, `skills/pm/SKILL.md`, `skills/quick-fix/SKILL.md`)

**Problem.**
- Pal Center 0.16.0 added Company mode, `pal-work wait-decision` and `pal-work hold`, and 0.21.0
  added `pal-work mode`. No skill names any of them.
- Phase 018 drafted a spec from an old note that said Company mode was off, and missed the decision
  flow.
- Phase 013's lead Roadmap card had no bundle line.

**Rule.** Answer 1. The new reference holds the rules. The phase skill's **Owner stops** gets a
one-line pointer, and the skill is trimmed elsewhere to stay under its 250-line cap. The quick-fix
skill reads **Owner stops** already, so it follows the same rules. The pm skill's **Start** and
`/pm pickup` point to the reference.
1. **Mode first.** Every `/pm`, `/pm pickup`, phase start, phase resume and quick-fix start runs
   `pal-work mode --project <key>` (the `Work CLI:` path) before anything else. It never trusts a
   note or a memory about Company mode. With exit 5, no CLI line, or Pal Center older than 0.21.0,
   the session behaves as it does today.
2. **At a spec-review or findings stop** the session follows the last line of `mode`:
   - `owner stops: run wait-decision --phase NNN …` → do the usual stop steps (publish, set
     `waiting_on_owner`, push, notify). Then run `pal-work wait-decision --phase NNN` in the
     foreground with a Bash timeout of 600000 ms, and run it again on exit 3. The result:
     - `approved` or `defaulted` → use every recommended answer;
     - `changed: <text>` → use the owner's text;
     - `vetoed` or `none` → wait for the owner in the session, as today;
     - exit 4 or 5 → wait for the owner.
   - `owner stops: wait for the owner` → as today.
   The sign-off PR and the staging test are always the owner's.
3. **Never by default.** A question that involves money, a password or key, or anything public is
   held with `pal-work hold --phase NNN --reason "<why>"` before waiting, so it can never pass by
   default.
4. **Recording.** Each answer goes in `doc/decisions.md`. An answer that came from the default is
   marked `(used by default)`.
5. **Resume.** A resumed session whose seed says a decision ended runs `wait-decision` first.
6. **Bundle line.** Whenever `/pm` recommends work, it writes the `Bundle: … · vehicle: …` line on
   the lead Roadmap card in the same write as the move.

#### A2. Chores and pickup [93, 94, 6] (new `skills/pm/references/chores.md`; `skills/pm/SKILL.md`)

**Problem.**
- Pal Center's own pickup runs chores first (decisions 76 to 79), but a hand-run `/pm pickup` does
  not.
- Nothing tells a session how to register a chore.
- Pickup passes over a large backlog item without saying why.

**Rule.** Answer 2.
1. **The ladder gains a chores rung**, before **Approved card**. It takes a due card from the
   Roadmap board's `Chores (Active)` column. A card's timing line decides when it is due:

   | Timing line | Due when |
   |---|---|
   | `Every: day`, `week` or `month` | That long has passed since the card's `Last run: YYYY-MM-DD` line |
   | `When: before phase` | First thing in a session that starts a phase card |
   | `When: after phase` | After a phase reaches `done` |
   | No timing line | Once; the card then moves back to `Chores` |

   A chore may run beside a phase in the other session folder. A card with `Action: harness notes`
   is Pal Center's alone, so the skill leaves it.
2. **A chore session** follows the card's description and ends with a final review:
   - code goes through the quick-fix review and a PR;
   - a check-only chore files its findings as backlog issues with a short report.

   The session then writes the `Last run:` line on the card. It never edits the board's columns.
3. **Registering a chore.** When the owner asks for repeatable work, or a session sees work that
   repeats (the same fix three phases running, or a check every retro asks for), the session
   proposes a card: its title, its `Every:` or `When:` line, and a description to start from. It
   creates the card only after the owner's yes in the session, in the column the owner names
   (`Chores (Active)` by default).
4. **Why a card was skipped.** For each card or backlog item it passes over, pickup's report gives
   the rung and the reason in one line (for example "rung 3: needs a contract change"). The `/pm`
   note lists the items that can only run from an Approved card (a phase card, or one that needs
   spend or a decision) under "Needs Approved to run".

#### A3. The QA pass [72] (new `skills/phase/references/qa.md`; `manifest/manifest.go`, `state/state.go`, `templates/phase-state.yaml`, `practices/ssot_standard.md`, `skills/phase/references/signoff.md`)

**Problem.** Pal Center has an isolated QA environment (`npm run qa`: a daemon and UI with fakes,
decision 62), but the phase flow has no step that uses it.

**Rule.** Answer 3.
- `project.yaml` gains an optional `harness.qa_command`: a command line run from the SSOT root, such
  as `cd desktop && npm run qa`.
- `phase-state.yaml` gains `qa: none | running | passed | failed`, with `none` as the default.
  `pal-harness check` rejects other values. A missing `qa:` reads as `none`, so existing state files
  still pass.
- When `qa_command` is set, `signoff.md` section 5 (after the merge) runs `references/qa.md` before
  the staging test, or before ship under `no-owner-test`:
  1. start the QA environment;
  2. follow each bundle feature's test script, or each What to expect now line;
  3. record pass or fail, with a screenshot of each, in `specs/NNN-slug/qa/` (a `summary.md` and
     `screens/`).
- A failure is a fix round, handled like a failed staging step under fix now. After 3 rounds it
  becomes an owner stop (`kind: findings`). With `qa_command` unset, nothing changes.
- The staging-test message links the QA summary.

#### A4. The UAT queue [65] (new flow override `uat-queue`; `manifest/manifest.go`, `skills/phase/SKILL.md`, `references/staging-test.md`, `references/signoff.md`, `references/ship.md`, `skills/pm/SKILL.md`)

**Problem.** One staging test at a time means each unanswered test blocks the next phase's sign-off.
This was the owner's idea, from 2026-11-17.

**Rule.** Answer 4. `uat-queue` joins `FlowOverrideNames`. It is off for every project until its
`project.yaml` turns it on. Under it:
1. **Park.** If the staging test is still unanswered 20 minutes after the ping, it is parked as
   awaiting UAT:
   - `waiting_on_owner` stays set;
   - the work state becomes `waiting`;
   - the session keeps `wait-results` armed;
   - `/pm pickup` may start the next card.
2. **Queue.** A later phase's sign-off PR does not wait for the earlier test. Up to **3** phases may
   sit merged on `staging`, each waiting in its own session. A fourth sign-off waits as today.
3. **One test.** The staging-test message for the newest phase lists every queued phase's steps, so
   the owner tests once.
4. **One promotion.** When every queued phase is passed or deferred, the **oldest** phase's session
   promotes `staging` → `main`. Every other session sees that `main` already holds its sign-off merge
   commit, skips the promotion, and does the rest of ship (deploy check, statuses, retro, close-out).
   Each session writes only its own phase's state.
5. **Hold.** A failed step in a phase that a later queued phase builds on holds the whole batch
   until it is fixed now or deferred. Steps that publish anything stay must-wait.
6. Pal Center's screen for the queue is product work, not part of this release.

### Part B: CI, memory and subagents

#### B1. No push while CI runs; the watch under `timeout` [78, 85] (`practices/devops_cicd.md`, `skills/phase/SKILL.md` Saved state)

**Problem.** The CI gate cancels the older run on a newer push, so a session's own state or docs
push cancelled a running CI and cost a re-run (phases 007 and 017). A 9-minute watch was still
moved to the background.

**Rule.** Answers 5 and 6. **Waiting on CI and merging** gains:
- **Hold pushes.** While a PR's CI runs, commit to that PR's branch locally (state, log, docs) and
  push once the watch ends, all in one push. This is an exception to **Saved state** step 3, safe
  because a CI run is shorter than the 1-hour stuck limit. Pushes to other branches go on as usual.
- **The watch** is `timeout 520 gh pr checks <n> -R <owner/repo> --watch --interval 30` with a Bash
  timeout of 540000 ms. Exit 124 means it is still running: run the same command again. The same
  applies to `gh run watch`.

#### B2. Memory before lint, mocks and tests; smaller retries [84, 91, 60, 32, 89] (`practices/devops_cicd.md`, `practices/go_api.md`, `practices/testing.md`)

**Problem.** Lint, `make mock` and full test runs were cut short for low memory (phases 016 and
018). The session then re-ran everything, or pushed over the cut. `make mock` took over 10 minutes
on the owner's PC. Jest reports were stopped twice in LFPV phase 008.

**Rule.**
1. **Free memory before heavy runs** adds `make lint` and `make mock` to its list. Every heavy
   command (mock, lint, test, build) runs in the foreground with a Bash timeout of 600000 ms, never
   `run_in_background`.
2. **A run cut short by low memory is run again, never pushed over:**
   - lint is run again;
   - `make test` is re-run one package group at a time, with `GOFLAGS=-p=1`, retrying only the group
     that was cut;
   - when `make mock` is stopped, the implementer runs `mockery --name <Interface>` for the
     interfaces its task changed, and the phase runs the full `make mock` once before the PR
     (`go_api.md`, **Mocks.**).
3. **Jest** full runs and the report command pass `--maxWorkers=2`.
4. **Startup waits.** A test with a fixed health or startup wait reads its limit from one CI-scaled
   constant: longer when `CI` is set or on the self-hosted runner. Phase 017 failed on a 15-second
   wait in an unrelated test.

#### B3. Subagents [9, 10, 90, 108, 73, 86] (new `skills/phase/references/subagents.md`; `references/build.md`, `references/review.md`)

**Problem.**
- Implementers looped on finished reports (phases 005 and 006).
- Stale replies were accepted (phase 006).
- The same review findings came back every phase: a lock held across a network call came back in
  phases 016 and 017.
- A silent test timeout hid a broken test (phase 015).
- Owner-facing wording was left to the final review.

**Rule.** Answer 7. `build.md` is at its 150-line cap. Its **Larger phase** steps 1, 3 and 4 move
into `subagents.md`, which `build.md` points to. The new file adds:
1. **Controller.**
   - Stop an implementer with TaskStop the second time it repeats a finished report or reports
     "waiting on background work".
   - Accept a reply only when it answers the latest fix message: the reply quotes that message's
     first line. Otherwise send it back.
2. **The brief** tells implementers:
   - never to wait on their own background work;
   - to read the full test run's exit code, and to report a timeout as a failure, never as a pass;
   - to check the **known findings** list before reporting:
     - no lock held across a network call;
     - a retry re-reads its rule and its target;
     - a missing source shows as a visible state, never a silent pause;
     - `openapi` required fields match the handler.
3. **The task reviewer** also checks owner-facing wording: no jargon, the order the owner sees
   things in, and reason names that match the docs.
4. **Stale editor warnings.** Language-server diagnostics are ignored when `go build`, `go vet` and
   the tests pass (`build.md` and `review.md`).

#### B4. Session habits [24, 55, 77, 67] (`practices/workflow.md`)

**Problem.**
- A fixer committed on a detached HEAD (LFPV phase 006).
- A temporary auto-mode check failure stalled a session.
- Inline heredoc PR bodies broke on backticks.
- Missing npm dependencies were found only at the first test run.

**Rule.** A new **Session habits** block:
- before every push, `git -C <path> symbolic-ref -q HEAD` must name the branch (a fixer on a
  detached HEAD stops), and after the push the local tip must equal `origin/<branch>`;
- a temporary auto-mode check failure is retried after a short wait, with other work going on
  meanwhile, and is never an owner stop;
- every PR body is written to a file and passed with `--body-file`;
- at session start, each component with a `package.json` and no `node_modules` (or one older than
  the lockfile) runs `npm ci` before the first test run.

### Part C: Plans, specs and reviews

#### C1. Plan review [5, 68, 56, 51, 45] (`agents/review-plan.md`, `skills/phase/references/plan.md`, `templates/plan.md`, `practices/react_native.md`)

**Problem.**
- Plan reviews took three rounds where the last ones had only minor findings (phase 005: 9 minors,
  then 2).
- Task file lists missed files.
- Delete tasks missed link and junction cases (phase 012).
- A mobile phase shipped without an app version bump (LFPV phase 011, hotfix lfpv-mobile#51).
- A native dependency upgrade broke passkeys on a device although every test passed (LFPV phase 010,
  androidx.credentials).

**Rule.** Answers 8 and 10.
- A round with only minor findings ends the review. The session applies them and notes "minors
  applied, no re-review".
- Check 17, **File lists**: each task's file list holds every file its code and tests name.
- A **Deletes and locks** row for a delete helper names its link and junction test cases.
- Every phase that changes the mobile app has a task that bumps the app version (the runbook's
  release step), whatever the flow overrides.
- A task that adds or upgrades a native dependency records the resolved versions of the shared
  libraries it pulls in, against the existing native modules (for example
  `./gradlew :app:dependencies` filtered by the library). A mismatch is a major finding.

#### C2. The spec [82, 102, 12, 38, 57] (`skills/phase/references/spec.md`, `templates/spec.md`, `templates/plan.md`, `practices/workflow.md`)

**Problem.**
- New features asked for during spec review grew the spec.
- Phase 018 had 5 spec revisions and 6 Codex doc rounds.
- A feature needing hardware the owner could not reach was signed off as tested.
- A spec fixed an app package that did not match the store app.
- The plain-English rule was added mid-phase.

**Rule.** Answer 9.
- **A new feature asked for during spec review** becomes its own card by default (`todo` in
  `features.yaml`), with at most one line in the spec.
- **Live spec changes.** Keep one running list of the owner's rulings in the spec, and re-run the
  Codex doc check once per batch of changes, not once per message.
- **Hardware the owner can't reach.** A step that needs it is marked `unverified: <reason>` in the
  spec, and the sign-off PR lists it.
- **Store identity.** Before a spec fixes an app package or bundle id, read the package of the
  existing Play or App Store app and record it in the spec.
- **Plain English** (Pal Center decisions 43 and 44) becomes a rule for every project in
  `workflow.md`. Diagrams, UAT steps and test reports are written for the owner, in plain words.
  The spec and plan templates carry it from the start.

#### C3. Review checklists [7, 15, 21, 69, 74, 58, 88] (`agents/review-code.md`, `agents/review-errors.md`, `agents/review-tests.md`, `skills/phase/references/review.md`, `practices/testing.md`)

**Problem.** These findings each cost a fix round late in a phase:
- a 10-second client timeout against 15 seconds of chained adb calls (phase 006);
- a blanket error mapping that showed a network message for a TypeError (LFPV);
- concurrency and lifecycle findings, such as identity read after an await;
- something starting after a kill switch was thrown;
- a failed restore that left no notice (phase 015);
- a failed Stop then Start, found only on retry (phase 012);
- a made-up 422 body that hid a real bug (phase 017).

**Rule.**
- **`review-code`:**
  - every client timeout is at least the server's chained call budget;
  - concurrency and lifecycle checks: a lock, undo, sign-in, and identity read before an await. The
    first task that touches shared state gets these checks in its own per-task review, not only at
    the end;
  - for a feature with a global stop or kill switch: can anything start after it is thrown?
- **`review-errors`:**
  - an "any error becomes unavailable" mapping must not swallow programming errors (TypeError,
    ReferenceError, nil dereference); those show a generic error;
  - for each multi-step operation: what does the owner see if a later step fails?
- **`review.md`:** after each fix round, the reviewer re-checks the failure path and the retry.
- **`testing.md` and `review-tests`:** an error-path fixture (a 422, 409 or 503 body) is copied from
  a real response (a handler test's output or the `openapi` example), never written by hand.

#### C4. Tests and checks [16, 13, 76, 106, 29, 47] (`practices/testing.md`, `agents/review-tests.md`, `practices/react_native.md`, `templates/screens.spec.ts`, new command `pal-harness utf8`, `.github/workflows/ci-gate.yml`, `state/state.go`)

**Problem.**
- The 1 ms timer steps on Windows read as a 33% slowdown.
- Jest shims exported functions the native module lacks.
- Full-page screenshots cut off content inside an inner scroll container.
- A Windows-1252 byte got into a UTF-8 file (phase 019).
- Named extra checks were folded into the last step's note, and a session wrote a `fix:` field that
  was rejected.

**Rule.** Answers 11, 12 and 13.
- **Speed check:** 10 pairs by default. A slowdown counts only when the p95 is both over 20% and
  over 2 ms slower (`testing.md`, `review-tests` check 5).
- **Jest shims** for native modules export only what the native module exports. A parity test
  compares the two lists.
- **`screens.spec.ts`** lets inner scroll containers grow to their content before a full-page
  capture.
- **`pal-harness utf8 [dir]`:**
  - It checks every file git tracks (`git ls-files`) and skips binary files (a NUL in the first
    8000 bytes, git's own test).
  - It prints `<path>:<line>: not UTF-8` for each bad file, then exits 1. Exit 0 means clean. Exit 2
    means usage, or not a git repo.
  - The reusable `ci-gate.yml` runs it before fingerprinting, so every repo on the CI gate gets it.
    A failure makes the gate red, so the whole run is red.
- **`features.yaml` results** take `check: <name>` (lower-case words and dashes) in place of
  `step:` for an extra check outside the test script. Exactly one of the two is set.
- **Unknown fields.** An unknown field in a result gets the finding "allowed fields: date, env, step,
  check, result, note, issue". Steps and the feature itself get the same kind of finding.

### Part D: Owner tests, release and records

#### D1. Owner tests [28, 30, 36, 35, 50, 31] (`skills/phase/references/staging-test.md`, `references/spec.md`, `templates/spec.md`, `practices/workflow.md`)

**Problem.**
- The owner spent about 10 minutes setting up two test roles before every LFPV test.
- Pre-flight missed Docker being down.
- `pm clear` was denied in auto mode.
- "Go offline" read as the owner leaving.
- A destructive step made a partial run unclear.
- A split plan was acted on before the owner confirmed it.

**Rule.**
- **A two-role seed.** A project whose tests use two roles keeps one seed script: the sign-ups, the
  shared data, the invite and sample entries. The first phase that needs it adds the script as a
  plan task. Staging tests run it, so the owner never builds the setup by hand.
- **Pre-flight adds:**
  - Docker running (`docker info`) when the stack uses it;
  - the adb server up;
  - the app's data reset on each test phone with `adb shell pm clear <package>`. A mobile project
    allows exactly that command in its `.claude/settings.json`. A project that cannot allow it ships
    a debug-only reset in the app instead.
- **Step wording.** A step names exactly what to stop or start ("stop the API only; leave Metro
  running"). Going offline is written as the phone action ("turn on airplane mode on the phone").
- **Destructive or optional steps** (such as removing the phone's screen lock) go in their own
  feature with their own script, so skipping them is an explicit partial run.
- **A split plan from the owner** ("this session reviews, the next pickup builds") is restated in one
  line, and the session waits for a yes before acting.

#### D2. Release and devops [39, 40, 41, 42, 43, 48, 49] (new `templates/runbook-android-release.md`; `skills/phase/references/plan.md`, `references/ship.md`, `practices/devops_cicd.md`, `practices/go_api.md`)

**Problem.**
- LFPV's first Play release found the EAS keystore, upload-key and Play Console steps mid-run.
- Auto mode refused commands that only the owner may run (`terraform apply` on production,
  `gh workflow run`, adb).
- A Vercel project deployed with the wrong root folder and branch.
- Cloud Run kept serving the old revision after terraform.
- The proxy-trust setting could not be confirmed from the logs.
- A runbook named `terraform.tfvars` where the owner has `production.tfvars`.
- Projects on hosted runners ran out of free minutes.

**Rule.** Answers 14 and 15.
- **New `templates/runbook-android-release.md`:**
  - the EAS credentials (one keystore, and which one a second terminal downloads);
  - the lock on the first upload key;
  - the Play Console draft steps (Add from library, the advertising ID question).
- **Owner-run commands.** The plan lists, under that heading, every command only the owner can run,
  with the exact text. `ship.md` hands them over as one numbered list instead of finding them
  mid-run.
- **`devops_cicd.md` rules:**
  - **Vercel:** a project is set up with its root folder and production branch before the first
    deploy, and a production redeploy is tried on a preview first.
  - **Cloud Run:** after `terraform apply`, traffic stays on the old revision until the deploy
    workflow runs, so the runbook runs it next.
  - **Self-hosted runners:** a repo that runs out of free minutes moves its heavy jobs to the
    self-hosted runner, with the `WINDOWS_RUNNER` variable pattern shown in `templates/ci.yml`.
- **`go_api.md` release checklist:** in production the API logs a hashed or shortened client
  address, so the proxy-trust setting can be confirmed from the logs.
- **`ship.md`:** before ship, the session dry-reads every command and file name in the phase's
  runbooks against the owner's real files, and fixes any mismatch first.

#### D3. Trial measures in the retro [64] (`agents/retro.md`, `templates/retro.md`)

**Rule.** Answer 16. The retro gains an **Owner stops** section:
- each stop: its kind, how long it waited, and whether it could have been a decision under Company
  mode;
- a one-line count.

There is no state schema change. Note #64 stays open in Pal Center until the owner's LFPV run with
