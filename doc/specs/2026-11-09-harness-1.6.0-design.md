# pal-harness 1.6.0: Pal Center phase 009 and LFPV phase 003 notes

**Status:** Draft, waiting for the owner's approval (questions answered 2026-11-09: "accept all").
**Source:** 10 harness notes, filed as althenlimzixuan/ai-workshop#29 to #38, from Pal Center's
phase 009 retro (notes 1 to 8) and LFPV's phase 003 and 004 retros (notes 9 and 10), started from
Pal Center's Start work (session HARNESS-work-4F7BTD).
**Delivers:** pal-harness 1.6.0: two new commands (`mem`, `adb`), one new template (a Playwright
screenshot file) and rule text. It is a minor version because it adds commands. The planned
`upgrade` command moves to 1.7.0 (your answer 1).

## Summary for the owner

1. **Every page gets screenshots in UI phases.** The harness ships a Playwright file that saves each
   page in light, dark and the narrowest width. The review stage runs it when screens changed. The
   UI reviewers read the pictures and the sign-off PR shows them to you.
2. **"The data already exists" gets checked when the spec is written.** The spec lists each figure
   with the endpoint and field that serves it. A figure nothing serves becomes a contract row or a
   question, not a surprise at planning.
3. **A plan's grep and lint gates are tried before the plan review.** The plan carries a table
   showing what each gate matches today and that it catches a planted bad sample. A gate that flags
   correct code, like phase 009's amber grep, is a major finding.
4. **No task passes without its failing-test evidence.** The implementer's report shows each new
   test failing, then passing, and the per-task reviewer rejects a task without it.
5. **UI tasks get two more review checks.** The warning colour (amber) marks only states where the
   user needs to act, and the window's edges (smallest size, both sides of each breakpoint) are
   tested.
6. **A restyle cannot drop a badge or a figure quietly.** A restyle task first lists the screen's
   behaviours and data, with a test for each item.
7. **Deferred minors reach `doc/later.md`.** At the end of the build the session copies the minors
   parked in the build ledger into `doc/later.md`, so they are not lost.
8. **You're told where to turn auto review on.** When Codex is skipped because auto review is off,
   the sign-off PR and your message name the place. The switch on Pickup or Work goes to Pal Center as
   a product capture.
9. **One command brings the test phones back.** `pal-harness adb` reconnects each phone in
   `doc/devices.yaml` (including the second test account's phone), finds a changed wireless port, and
   sets the reverse ports. Metro's file-watching rule now names fix rounds.
10. **Heavy runs wait for free memory.** `pal-harness mem` runs before the reports, full test runs
    and heavy builds. Under 2 GB free the session frees what it started, waits up to 9 minutes,
    then goes on with a logged warning.

## Changes

Each change lists the problem, the new rule and the files. Note numbers are in brackets (the list at
the end).

### 1. A screenshot file for UI phases [29] (new `templates/screens.spec.ts`, `skills/phase/references/review.md`, `templates/signoff-pr.md`, `agents/review-ui.md`, `practices/testing.md`)

**Problem.** In Pal Center's phase 009, a one-off script took a screenshot of every page from the
e2e stack. The UI reviewers and you both used them. The script was not kept.

**Rule.** Your answer 2: A.
- `templates/screens.spec.ts`: a Playwright test that, for each page in its `pages` list, theme
  (light, dark) and width (the project's default and its narrowest supported size), opens the page,
  waits for the network to go quiet and saves a full-page PNG named `<page>-<theme>-<width>.png`
  into the folder in `SCREENS_DIR`. The theme is set through `prefers-color-scheme`. A project whose
  theme is an in-app setting edits the one marked `setTheme` hook.
- A web or desktop project copies it once into its e2e folder (the first UI phase that has no copy
  adds a task for it) and lists its pages. It runs on the project's existing Playwright set-up (its
  `webServer` or global setup starts the app). `testing.md` gets a **Screenshots** bullet that says
  so.
- `review.md` section 1: when the phase changed something on screen and the project has the file,
  run it once on the final commit, beside the reports:
  `SCREENS_DIR=<set>/specs/NNN-slug/screens npx playwright test <e2e folder>/screens.spec.ts`.
  The PNGs are committed on `docs/NNN-slug`. A failed run is fixed like a failing test. No copy and
  no task for one is a recorded skip.
- `pal-review-ui` gets the folder and reads the PNGs (it can read images) alongside the code. The
  Codex `uiux` review is told the folder path.
- `signoff-pr.md` gains a **Screens** section: each page's light and dark PNG at the default width,
  as images linked from `docs/NNN-slug` (`https://github.com/<owner>/<repo>/blob/docs/NNN-slug/<path>?raw=true`),
  and a link to the folder for the rest.
- React Native screenshots (Maestro) come later, when a mobile UI phase asks.

### 2. "Already exists" names its source [30] (`skills/phase/references/spec.md`, `templates/spec.md`, `agents/review-plan.md`)

**Problem.** Phase 009's spec said "every number already exists in the API" and listed a PRs
"Merged" group the API does not serve. Nobody checked until the plan review.

**Rule.** A call (no question):
- When a spec says, or relies on, a screen's data already being served, it gets a **Data sources**
  table: each figure, list or badge, the endpoint and field that serves it, and how it was checked
  (`doc/openapi.yaml` line or the handler's file and line). It is filled while drafting, before the
  Codex spec review.
- A figure with no source becomes a row in **Contract** (the phase adds it) or a numbered question.
- The plan reviewer checks that every figure in the UX outline is either in **Data sources** or built
  by a task; a figure in neither is a major finding.

### 3. Gate dry-runs before the plan review [31] (`skills/phase/references/plan.md`, `templates/plan.md`, `agents/review-plan.md`)

**Problem.** Phase 009's plan used a raw-colour grep as a gate. It matched the amber token names, so
it flagged correct code and could not serve as the gate.

**Rule.** Your answer 3: A.
- A **gate** is any grep, lint rule or script in a task's prove-it commands whose result decides
  whether the task is done (not the repo's normal lint and tests).
- Before dispatching `pal-review-plan`, the session runs each gate on the current tree and adds a
  **Gate dry-runs** table to the plan: the gate, its result today (each match marked as a real hit or
  a false hit), and its result on one planted bad sample (a scratch file with one violation, deleted
  after). A gate must pass on code that follows the rule and fail on the sample.
- A gate with a false hit or one that misses the sample is fixed before the review.
- The reviewer checks the table exists for every gate and repeats each grep with its search tool. A
  missing row is a minor finding; a false hit or a missed sample is a major finding.

### 4. RED before GREEN, enforced by the task reviewer [32] (`skills/phase/references/build.md`, `skills/quick-fix/SKILL.md`)

**Problem.** In phase 009 (and LFPV's phase 003 and 004), implementers' reports lacked the failing
run, or showed RED made later by mutation. The per-task reviewer did not reject them.

**Rule.** A call (no question):
- The implementer's report shows, for each new test, the RED output (the command and the failing
  lines that name the test) before the code, then the GREEN output. One red run is enough when every
  new test shows failing in it.
- build.md section 3: the session's dispatch to sdd's task reviewer adds the harness's checks
  (change 5 and 6 add more). The first: **reject the task when the report lacks a RED run for any new
  test, or the RED came after the code** (a commit order or a mutation note shows it). The rejection
  counts as one of the task's fix rounds.
- The session's own check of the report stays.
- A quick fix shows the same RED then GREEN in its log entry.

### 5. Two checks for UI tasks [33] (`skills/phase/references/build.md`, `agents/review-ui.md`)

**Problem.** Phase 009's per-task reviews kept finding amber used for states that were not "needs
you", and missing window-edge tests (the shadcn sidebar going off-canvas below 768 px against the
760 px window minimum).

**Rule.** Your answer 4: A, for every project:
- **Warning colour only where the user must act.** The warning colour (amber in most design systems)
  marks only states that need the user to do something. Other states use neutral or info colours.
- **Window edges tested.** A screen's tests cover the smallest supported window or screen size and
  both sides of each layout breakpoint the screen uses.
- Both go into the task reviewer's dispatch for a task that changes a screen, and into
  `pal-review-ui`'s checklist.

### 6. A restyle keeps what the screen did [34] (`skills/phase/references/plan.md`, `templates/plan.md`, `skills/phase/references/build.md`)

**Problem.** In phase 009, implementers dropped existing behaviour and data in restyles (the
brief-error badge, the spend figures).

**Rule.** A call (no question):
- A task that restyles or re-lays-out an existing screen carries an **Existing behaviour** list in
  the plan: every badge, figure, link, control and state (empty, loading, error) the screen shows
  today, each with the test that covers it.
- An item with no test gets one, written first and passing on the old code, before the restyle.
- The task reviewer's dispatch for a restyle task adds: every item in the list is still on the screen
  and its test still passes.

### 7. Deferred minors to `doc/later.md` [35] (`skills/phase/references/build.md`, `skills/phase/references/review.md`)

**Problem.** In a larger build, per-task reviewers' minors that the session parks stay in sdd's
ledger (`<set>/.superpowers/sdd/<plan>/progress.md`), which is git-ignored and removed with the set.

**Rule.** Your answer 5: A.
- build.md section 6 gains a step before the PRs: read the ledger and take every parked or deferred
  finding. A real bug becomes a backlog issue (review.md section 5 step 1). Every other one becomes
  one line in `doc/later.md` on `docs/NNN-slug`:
  `- YYYY-MM-DD — <finding> (source: task review, Task K, phase NNN)`. Commit and push.
- A finding fixed later in the build is skipped; the log entry says how many were carried.
- The whole-branch review's code reviewer is given the ledger path and flags a parked finding that
  is in neither place (minor).

### 8. Where to turn auto review on [36] (`skills/phase/references/review.md`, `skills/phase/references/signoff.md`, `skills/quick-fix/SKILL.md`)

**Problem.** In LFPV's phase 003 Codex was skipped because auto review was off for the project. You
found the switch hard to find (Projects → project → Reviews).

**Rule.** Your answer 6: A.
- When `pal-review` exits 5 and the reason says auto review is off, the `codex.skipped` entry, the
  sign-off PR's review table and the next owner message add: "turn it on in Pal Center at Projects →
  <project> → Reviews".
- *Pal Center product capture* (filed with `pal-capture` during the build): show the per-project
  auto review switch on the Pickup or Work tab, and name where to turn it on in `pal-review`'s skip
  message.

### 9. Metro in fix rounds, and the adb helper [37] (`practices/react_native.md`, `skills/phase/references/staging-test.md`, new command `pal-harness adb`)

**Problem.** In LFPV's phase 003 Metro was started with `CI=1` (no file watching), and after each
gap the wireless link, the reverse ports and the second phone were set up again by hand.

**Rule.** Your answer 7: A.
- `react_native.md` (Device testing): the Metro line already forbids `CI=1`. It now says it holds in
  every fix round and restart too.
- New `doc/devices.yaml` in a mobile project (format in `react_native.md`):
  ```yaml
  ports: [8081, 8080]          # adb reverse, each device
  devices:
    - name: Samsung A26        # what the owner calls it
      role: primary            # or second-user
      serial: R5CX...          # adb's USB serial; matches the wireless mDNS name
      wireless: 192.168.1.23:41234   # last known connect address
  ```
  Names and addresses only: no pairing codes.
- `pal-harness adb [dir]` reads it and, for each device:
  1. if `adb devices` already lists it as `device`, keep it;
  2. else `adb connect <wireless>`; if that fails, look the device up in `adb mdns services`
     (`_adb-tls-connect._tcp`, matched by its serial, else its IP) and connect the address found;
  3. then `adb -s <device> reverse tcp:<port> tcp:<port>` for each port.
  It prints one line per device (ready, or what failed) and, when an address changed, the new one to
  save. It never runs `adb disconnect` or `adb kill-server`. A device that still fails gets the
  owner message: "on <name>, open Settings → Developer options → Wireless debugging → Pair device
  with pairing code, and send me the code and the port".
  Exit 0: every device ready; 1: a device not ready; 2: usage, no `doc/devices.yaml`, or no `adb`.
- `react_native.md` and staging-test pre-flight step 3 run `pal-harness adb` instead of the manual
  steps; a two-person test script names which device each account uses.

### 10. Free memory before heavy runs [38] (`practices/devops_cicd.md`, `skills/phase/references/build.md`, `review.md`, `staging-test.md`, `skills/quick-fix/SKILL.md`, new command `pal-harness mem`)

**Problem.** In LFPV's phase 003 the PC was often short of memory: installs were killed and runs died
mid-way.

**Rule.** Your answer 8: A.
- `pal-harness mem [--min 2GiB] [--wait 9m] [--every 30s]` prints the available physical memory and
  the minimum. With `--wait`, it re-checks every `--every` until memory is above the minimum or the
  wait ends. Exit 0: enough; 1: still under the minimum; 2: usage or a platform it cannot read
  (Windows and Linux are supported).
- A new **Free memory before heavy runs** bullet in `devops_cicd.md`. Before the test reports, a full
  test run (the full check, a fix round's check), a release or native build (Tauri, local Gradle or
  EAS, Docker) and an app install on a phone:
  1. run `pal-harness mem`;
  2. under the minimum: stop what the session started and no longer needs (an emulator, an old dev
     server, Metro from another checkout), then `pal-harness mem --wait 9m` in the foreground (Bash
     timeout 600000 ms);
  3. still under: run anyway and write `low memory: <free> free before <run>` in the log.
- build.md, review.md (reports), staging-test.md (pre-flight step 4, which now uses the command) and
  quick-fix point to the bullet.
