## Summary for the owner

1. **CI stops re-testing files that already passed.** A project's CI asks the harness's gate first.
   Each job lists the files it reads; when those files already passed, the job is skipped. Docs-only
   and `specs/**` pushes, the push after a merge and promotions no longer run the full suite on your
   PC's runner. A newer push cancels the older run on the same PR or branch.
2. **A session waits on CI without parking for you.** It keeps one foreground watch. When Claude Code
   kills the watch for low memory, the session waits for memory and watches again. It no longer stops
   and waits hours for you.
3. **Nothing merges while CI is still running.** Before every merge the session reads the checks'
   exit code on its own (8 means still running: wait). `ci:` in `phase-state.yaml` only takes green,
   red, running or none, so the ssot check stops failing on `pending`.
4. **Go mocks use the setup that works.** `mockery --all --output mocks` into a top-level `mocks/`
   folder, as LFPV does. `--keeptree` is gone.
5. **Stale `wire_gen.go` fails CI.** Go API CI regenerates it and fails when the committed file
   differs.
6. **Plans show their deletes and locks.** Every delete helper names the read-only check that its
   target is its own; every callback fired under a lock is listed with the lock. The plan reviewer
   rejects a plan without them.
7. **The CI-wait and wake-up features go to Pal Center.** `pal-work wait-ci` and the nudge when a PR's
   checks finish are Pal Center code; they are filed as one Pal Center product capture.
8. **RED evidence is already enforced.** Note 7 shipped in 1.6.0; nothing changes.

## Changes

Note numbers are in brackets (the table at the end).

### 1. The CI gate [39, 43, 46] (new `.github/workflows/ci-gate.yml`, `.github/workflows/ci-mark.yml`, new command `pal-harness fingerprint`, new `templates/ci.yml`, `practices/devops_cicd.md`, `practices/testing.md`)

**Problem.** Pal Center's phase 003 ran 16 full CI runs where about 4 tested new code. Two runs at
once on the one self-hosted runner timed out a test. Pal Center fixed this for itself in quick fix
004 (a gate job, a mark job, `refs/ci-passed/<job>/<fingerprint>`, a concurrency group); no other
project has it.

**Rule.** Answer 4: a Go command, not Pal Center's Node script.

- **`pal-harness fingerprint [--rev HEAD] [--with <path>]... [--dir .] <spec file | ->`.** The spec
  has one line per job, `<job>: <path> <path> ...` (`#` starts a comment). For each job it prints
  `<job>=<fingerprint>`, in spec order. The fingerprint is the SHA-1 of the job name and one line per
  path, `<path> <git object id at rev>` (or `missing`), over the job's paths plus every `--with` path.
  A path may be a folder (its tree id) or a file. A new, changed or deleted file under a listed path
  changes it; any other file does not. Job names are `[a-z0-9][a-z0-9_-]*` (they go into ref names);
  paths are relative, with no `..`. Exit 0 printed; 2 usage, a bad spec, or not a git repo. It runs
  locally too: "would my change skip the `api` job?"
- **`ci-gate.yml`** (reusable, `workflow_call`). Inputs: `version` (the harness version, validated as
  in `check.yml`), `jobs` (the spec text) and `shared` (extra paths every job reads, default empty).
  It checks out the caller, runs `pal-harness fingerprint --with .github/workflows/ci.yml` at
  `v<version>`, and looks up `refs/ci-passed/<job>/<fingerprint>` with `gh api`. Outputs:
  `decisions` (`{"api":"run"}` or `"skip"`) and `fingerprints` (`{"api":"<sha>"}`) as JSON. A skipped
  job is named in the run summary with its fingerprint. Any failure to read a ref means `run`.
  `permissions: contents: read`; no `${{ }}` inside `run:` (inputs go through `env`).
- **`ci-mark.yml`** (reusable). Inputs: `fingerprints` and `results` (the caller's `toJSON(needs)`).
  For each job whose result is `success` it creates `refs/ci-passed/<job>/<fingerprint>` at the
  commit; one that already exists is fine; a failure is a warning, never a red run (an unrecorded
  pass only means the files are tested again). `permissions: contents: write`.
- **`templates/ci.yml`**: the caller skeleton a project copies: the triggers (`pull_request`, `push`
  on `dev`/`staging`/`main`, `workflow_dispatch`), the concurrency group
  `ci-${{ github.event.pull_request.number || github.ref }}` with `cancel-in-progress: true`, a `gate`
  job, one example job with
  `if: ${{ !cancelled() && fromJSON(needs.gate.outputs.decisions || '{}').<job> != 'skip' }}` (a
  gate that failed or never started, such as no GitHub minutes left, runs everything), and a `mark`
  job. Changing `ci.yml` (including the harness version in it) re-runs every job, since every job
  reads it.
- **`devops_cicd.md`**: **CI runs and minutes** gains **The CI gate** bullet: every repo with a code
  CI uses the gate; each job's line in the spec lists everything the job reads (code, build files,
  lint config, a contract copy its drift check compares); a job that starts reading a new path adds
  it in the same PR. The pipeline sentence "No stage may be skipped; the one exception is the tests
  on a promotion whose tree hash already passed" becomes "... the one exception is a job whose
  fingerprint already passed (the CI gate)". The same in **Branch & Merge Strategy** and in
  `testing.md`, **Test reports**.
- The SSOT repo's `ssot` check keeps running on every push, `specs/**` included: it validates
  `phase-state.yaml`, and it runs on GitHub's machines, not the owner's PC.
- Projects adopt the gate by one quick fix each after they re-pin (out of scope here). Pal Center
  swaps its own `ci-gate.mjs` for it then.

### 2. Waiting on CI and merging [39, 40] (`practices/devops_cicd.md`, `skills/phase/references/build.md`, `review.md`, `signoff.md`, `ship.md`, `staging-test.md`, `skills/quick-fix/SKILL.md`, `skills/pm/SKILL.md`)

**Problem.** Quick fix 002 parked for the owner three times, hours each, when Claude Code killed its
CI watch for low memory; the quick-fix skill never named the watch rule, so the session made up
background watchers. PR #55 merged while CI was still running (the checks were read through a pipe,
which hides the exit code), and a session wrote `ci: pending`, which the ssot check rejects.

**Rule.** Answer 6. The **Watching CI** bullet in `devops_cicd.md` becomes **Waiting on CI and
merging**:

1. **Wait** with one foreground `gh pr checks <n> -R <owner/repo> --watch --interval 30`, Bash timeout
   540000 ms (as today). Never `run_in_background`, Monitor or a background loop.
2. **A watch that ends without its own exit code** (the tool says it was killed, interrupted or timed
   out) is run again. From the second such end in a row, run `pal-harness mem --wait 9m` first. It is
   never an owner stop: no `pal-work hold`, no `waiting` status, no limit on retries.
3. **Merge guard.** Before every `gh pr merge`, run `gh pr checks <n> -R <owner/repo>` on its own,
   with no pipe, and read its exit code: `0` every check passed or was skipped → merge; `8` still
   running → back to step 1; `1` a check failed → read the run (**Read a red run before fixing
   it**). The spending-limit case keeps its local-evidence rule.
4. **`ci:` values.** `phase-state.yaml` `ci:` is only `green`, `red`, `running` or `none`
   (`pal-harness check` rejects anything else). Exit 8 is written `running`; never `pending`.

Every place a skill merges or sets `ci:` points to this bullet by name: the phase references, the
quick-fix skill (its step 5 now says to wait and merge this way, and lists the four `ci:` values),
and the pm skill. `templates/phase-state.yaml` already lists the four values.

### 3. CI-wait and wake-up go to Pal Center [41, 42] (product capture, no harness file)

**Problem.** A session has no way to wait on CI except `gh pr checks --watch`, and nothing wakes an
idle session when checks finish (pal-hook adds context only on a new prompt; Slack alerts cover only
`[HUMAN GATE]` PRs).

**Rule.** Answer 2. Both are Pal Center code (`pal-work`, the daemon's 2-minute PR poll). During the
build, one Pal Center product capture is filed with `pal-capture`: "`pal-work wait-ci <pr>` blocks on
the daemon's PR poll until checks finish (exit codes like `gh pr checks`), and Pal Center nudges a
session parked on CI when its PR's checks turn green or red". The PR closes #41 and #42 with a line
naming the capture. When Pal Center ships `wait-ci`, a later harness release makes it step 1 of
change 2.

### 4. Go mocks: the setup that works [lfpv-docs#20] (`practices/go_api.md`, `practices/testing.md`)

**Problem.** `mockery --all --keeptree --dir internal --output internal/mocks` does not work with
`internal/` paths. LFPV's api runs `mockery --all --output mocks` and it works.

**Rule.** Answer 5:
- `make mock` is `go run github.com/vektra/mockery/v2@v2.53.7 --all --output mocks`: every interface
  in the module, written flat into a top-level `mocks/` folder as package `mocks`, imported as
  `<module>/mocks`. `.mockery.yaml` holds the same settings (`all: true`, `output: mocks`).
- Flat output means one file per interface name, so **interface names are unique across the
  module**; two interfaces with the same name overwrite each other's mock.
- The project tree in `go_api.md` shows `mocks/` at the top, not `internal/mocks/`; the sentence about
  `internal/` mirrored paths goes. The Mocks row in the stack table names the command. `testing.md`'s
  Go bullet says the same.

### 5. Generated code drift: `wire_gen.go` [47] (`practices/go_api.md`, `practices/devops_cicd.md`)

**Problem.** Pal Center shipped 0.8.0 with a stale `wire_gen.go`, so seed files were not deleted
(phase 005 retro).

**Rule.** Answer 8, wire only:
- The pipeline table in `devops_cicd.md` gains a **Generated code** row: Go API runs `make wire` then
  `git diff --exit-code` (any change to `wire_gen.go` fails the job); Next.js and React Native: `—`.
- `go_api.md` (Make Targets) adds: CI runs `make wire` and fails on a diff, so commit
  `wire_gen.go` with the `wire.go` change that needs it.

### 6. Deletes and locks in the plan [45] (`agents/review-plan.md`, `templates/plan.md`, `skills/phase/references/plan.md`)

**Problem.** Pal Center's phase 003 built a deadlock (a callback fired while a lock was held took the
same lock) and a cleanup that deleted a folder the user picked (pickFolder). Both could have been
seen in the plan.

**Rule.** Answer 7:
- `templates/plan.md` gains a **Deletes and locks** section ("none" when no task has either):
  - each helper that deletes or cleans up files, folders, rows or keys: the task, what it deletes,
    and the **read-only check** that runs first and proves the target is one it created (a marker
    file it wrote, a path under its own root, a row it owns). A user-chosen path is never deleted
    without such a check;
  - each callback, event or hook fired while a lock is held: the task, the lock, and what the
    callback may take (it must not take the same lock, or one taken before it elsewhere).
- `plan.md` (the phase reference) tells the session to fill it while writing tasks.
- `pal-review-plan` gets check 16, **Deletes and locks**: a delete helper with no read-only check, or
  a callback under a lock that is not listed or that can take the same lock, is a major finding. Both
  join its earlier-majors `harness list` (items 6 and 7).

### 7. RED per test: already shipped [44] (no change)

**Problem.** Pal Center's phase 003 task 8 skipped RED.

**Rule.** Answer 3. pal-harness 1.6.0 (change 4) already requires the RED output for each new test
in the implementer's report and has the per-task reviewer reject a task without it. Phase 003 ran
