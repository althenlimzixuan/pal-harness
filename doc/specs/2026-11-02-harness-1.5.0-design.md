# pal-harness 1.5.0 — the open harness captures

**Status:** Approved (owner's answer of 2026-11-02: "accept all").
**Source:** 21 harness captures in Pal Center's inbox (`kind=harness`, `state=new`): 5 from Pal Center's
phase 001, 6 from LFPV's phase 003, 4 from ETP's phase 097 and 6 from LFPV's phase 004. A 22nd, "pin
pal-harness 1.4.2", is a re-pin and stays in the inbox for that step.
**Delivers:** pal-harness 1.5.0: rule text (practices, skill references, reviewer agents, one template)
and two new `pal-harness` commands, `log` and `contrast`. A minor version, because the commands are new.
1.5.0 also carries 1.4.2 (the full-width render fix), which is on `dev` and has not reached `main`.

## Summary for the owner

1. **Fewer CI minutes.** Windows and macOS jobs run once per change, on the pull request. When GitHub
   blocks a run on the spending limit, the session sees it at once, runs the same checks locally as
   evidence, and tells you. It does not spend fix rounds on it.
2. **Bot dependency PRs get CI and land first**, so a phase no longer trips over the same `expo-doctor`
   failure the bot already fixed.
3. **Sessions write only inside their worktree set.** Scripts get their target folder explicitly, and
   the new `pal-harness log` refuses a folder outside the set.
4. **Clock-stamped logs:** `pal-harness log` writes each `phase-log.md` entry and `last_progress_at`
   from the system clock, so no timestamp is typed by hand.
5. **Contrast is measured, not estimated:** `pal-harness contrast` gives the WCAG ratio, and the UI
   reviewer and the fixer both use it.
6. **The plan review catches more.** Every contract endpoint and appendix behaviour needs a task. Every
   key or secret handoff names who may receive it and how the sender checks them. Every test step is one
   you can actually run there.
7. **TDD order is checked, not taken on trust:** an implementer's or fixer's report without its red run
   is sent back.
8. **Lint runs in each task**, through the repo's own scripts, never a bare `npx prettier`.
9. **Reviewers save their own reports**, so the session no longer copies them by hand.
10. **The speed check is fair:** old and new code run in alternating pairs on the same machine, instead
    of against last phase's numbers from another day.
11. **Reports run cleanly on Windows:** a preflight checks the setup first, and Jest reports run one at a
    time.
12. **Ready for your test means ready.** A pre-flight checks the device, the tunnel, the accounts, a
    cold Metro start and free memory. A pairing code is asked for up front. The same checklist runs
    again when you come back after a gap.
13. **A fix that changes behaviour updates the test steps** it affects, before you run them.

## Changes

Each change lists the problem a project hit, the new rule, and the files. Capture numbers are in
brackets (the list at the end).

### 1. CI minutes and spending-limit blocks [1, 2] (`practices/devops_cicd.md`, `skills/phase/references/build.md`)

**Problem.** Pal Center's phase 001 ran CI twice per commit, a push run and a pull-request run. Windows
runners bill at 2x, and the Actions budget ran out mid-phase. The session then spent fix rounds on runs
that never started.

**Rule.**
- Triggers: `pull_request`, plus `push` only on `dev`, `staging` and `main`. Never a bare `push` (a work
  branch with a PR would run twice).
- Jobs on Windows or macOS runners (billed at 2x and 10x) run on `pull_request` only. The `push` runs
  keep the Linux jobs. Every change reaches `dev`, `staging` and `main` through a PR, so the PR run is
  the gate.
- A red run is read before it is fixed (`gh run view <id> -R <owner/repo>`). A job that never started
  because of the spending limit or a billing problem is not a code failure, and it is not a fix round:
  1. run the repo's CI commands locally on the PR's head (the same checks as **Check before every
     push**), and save the output as `specs/NNN-slug/reviews/local-ci-YYYY-MM-DD-HHmm.md`;
  2. send one "needs you: GitHub Actions spending limit reached on <repo> — CI ran locally instead"
     notification, and keep working (it is not an owner stop);
  3. keep `ci: red`, with the note `ci blocked: Actions spending limit; local CI green`. A PR into
     `dev` may merge on that local evidence (the merge gates in review, sign-off and quick-fix say so,
     and the block does not make the build "stuck"). The sign-off PR says CI did not run, so you
     decide at the gate.

*My call:* the capture also asked to move Windows CI to a self-hosted runner. That is an infrastructure
choice for Pal Center (a runner on your PC uses your PC, and a public repo must never use one), not a
harness rule. It goes to Pal Center's inbox as a product capture.

### 2. Bot dependency PRs [14] (`practices/devops_cicd.md`, `skills/phase/references/build.md`)

**Problem.** ETP's Expo drift workflow opened an "Expo patch pins" PR with `GITHUB_TOKEN`. GitHub starts
no workflow for such a PR, so it sat for a week with no CI. Phase 097 then hit the same `expo-doctor`
failure and spent a CI fix round on it.

**Rule.**
- A workflow that opens a PR with `GITHUB_TOKEN` also starts CI on it. `ci.yml` has
  `workflow_dispatch:`, and the bot workflow runs `gh workflow run ci.yml --ref <branch>` (with
  `actions: write`). `workflow_dispatch` is the one event `GITHUB_TOKEN` may start.
- Before cutting `feature/NNN-slug` in a repo, the phase lists the open bot PRs into `dev`
  (`gh pr list -R <owner/repo> --base dev --author app/github-actions`):
  1. no checks → close and reopen the PR (`gh pr close`, `gh pr reopen`). A reopen by the session
     fires `pull_request`, so the full CI runs, Windows jobs included, even in a repo whose `ci.yml`
     has no `workflow_dispatch:` yet;
  2. green → merge with `--merge`, then branch from the new `origin/dev`;
  3. red → leave it and note it in the log. If the phase's CI then fails on the same check, merge the
     bot's change into the phase branch instead of fixing it by hand. That merge is not a fix round.

### 3. Scripts write only inside the worktree set [3] (`skills/phase/SKILL.md`, `skills/phase/references/build.md`)

**Problem.** In Pal Center's phase 001, superpowers' `task-brief` script resolved its output folder from
the current folder. Sessions never `cd` into the set, so it wrote into your checkout.

**Rule.**
- A script that writes files gets its target as an absolute path inside the set. A script that resolves
  its target from the current folder is never run from the session's own folder. It runs in a subshell
  started in the set, `(cd <path in the set> && <script> …)`, which ends with the command, so the
  session's folder never moves.
- For `superpowers:subagent-driven-development`, `sdd-workspace` and `task-brief` run from the set's
  root, so their workspace is `<set>/.superpowers/sdd/<plan>/` (self-ignored). `review-package` runs
  from the component worktree the task changed, with its output in that workspace.
- Before running a writing script, check that the target starts with the set's path. If it does not,
  stop.
- `pal-harness log` (change 4) refuses a folder outside `.pal-worktrees/`.

*My call:* `pal-harness spec new` and `adr new` keep working outside a set. You may run them by hand in
your checkout, and the phase flow already passes the set's folder to them.

### 4. `pal-harness log` [15] (new command; `skills/phase/SKILL.md`, `skills/quick-fix/SKILL.md`, `practices/ssot_standard.md`)

**Problem.** ETP's phase 097 log had hand-typed timestamps, some of them in the future.

**Rule.**
- `pal-harness log <phase folder> <headline> [body file]` appends
  `## YYYY-MM-DD HH:MM — <headline>` (and the body file's text) to `phase-log.md`. It sets
  `last_progress_at` in `phase-state.yaml` to the same moment (RFC 3339 with offset). Both come from the
  system clock.
- The folder must hold `phase-state.yaml` and sit under `.pal-worktrees/`. Otherwise the command exits
  2 and writes nothing. Both files are replaced through a temp file and a rename. If the second write
  fails, the first file is put back.
- The phase and quick-fix skills use it for every log entry, after the `phase-state.yaml` write and
  before the commit. Neither the log stamp nor `last_progress_at` is typed by hand.

### 5. `pal-harness contrast` [4] (new command; `agents/review-ui.md`, `skills/phase/references/review.md`)

**Problem.** In Pal Center's phase 001, a contrast finding survived three fix rounds. The reviewer and
the fixer each estimated the ratio from `oklch()` values and disagreed.

**Rule.**
- `pal-harness contrast <foreground> <background>` prints the WCAG 2 ratio and whether it passes AA for
  text (4.5:1) and for large text and UI parts (3:1). It reads `#rgb`, `#rrggbb`, `rgb()` and `oklch()`.
  An `oklch()` value outside sRGB is clipped, and the output says so. A colour with alpha is refused:
  composite it over its background first.
- The UI reviewer measures every contrast finding with it, or from the rendered colour. The finding
  shows both colours, the ratio and the threshold.
- The fixer measures again after the fix and puts the new ratio in the fix's log entry. An estimate is
  not evidence.

### 6. The plan covers the contract and the appendix [5] (`agents/review-plan.md`, `skills/phase/references/plan.md`)

**Problem.** Pal Center's phase 001 plan had no task for `POST /update/notified`, which the spec's
contract listed. Only the code review caught it.

**Rule.** Every endpoint in the spec's `## Contract` and every behaviour in its Appendix maps to a task,
like every feature and test step. The plan reviewer lists any that have none.

### 7. Trust handoffs in the plan [16] (`agents/review-plan.md`)

**Problem.** In LFPV's phase 004 (vault keys and invitations), who may receive a key, and how the
sender checks them, came up only in review.

**Rule.** A task that hands over a key, a secret, a token or an invitation says who may receive it and
how the sender verifies the recipient. If the plan does not say, the plan reviewer raises a major finding.

### 8. Test steps the owner can run [12] (`skills/phase/references/spec.md`, `agents/review-plan.md`)

**Problem.** ETP's phase 097 spec had steps that hit the limits of where you test: the local stack's fake
file store, review accounts it does not have, and airplane mode, which drops the phone's wireless adb.
They surfaced during the test, not before you approved the spec.

**Rule.**
- When drafting, each step is checked against where you will test: staging or the local stack (its fake
  or stubbed services, which accounts exist) and the real phone (airplane mode or Wi-Fi off drops
  wireless adb, so an offline step says how to stay connected, by USB or on a build that needs no
  Metro).
- A step that cannot run there is rewritten, or moved to the automated tests with a line in Calls I
  made.
- The plan reviewer checks the same thing.

### 9. The red run comes first, and is checked [11, 17] (`skills/phase/references/build.md`, `skills/phase/references/review.md`, `skills/quick-fix/SKILL.md`)

**Problem.** In LFPV's phase 003, a subagent wrote code before its failing test, and the TDD order had to
be shown afterwards by mutation. In phase 004, fixers' reports did not always show a red run.

**Rule.**
- Each implementer brief says TDD is required for the task. The agent runs the fixture's test before the
  code and pastes the red run (the command and its failing output) in its report, then the green run.
- The controller checks every implementer's and fixer's report for that red run. If it is missing, the
  task goes back to the agent, and that counts as one of the task's fix rounds.
- A fix for a bug finding starts with a test that reproduces the bug, run red.

### 10. Lint in every task, through the repo's own scripts [8, 9] (`practices/workflow.md`, `practices/react_native.md`, `skills/phase/references/build.md`, `templates/plan.md`)

**Problem.** In LFPV's phase 003, sessions ran a bare `npx prettier` instead of the repo's script, and
lint errors such as `set-state-in-effect` were caught after the task, not in it.

**Rule.**
- Lint and format run through the repo's own scripts (`npm run lint`, `make lint`), never a bare
  `npx prettier` or `npx eslint`.
- Each task's prove-it commands include the repo's lint. A task is not done, and its per-task review
  does not pass, until lint is clean.
- The plan template's **Prove it** line names the lint command.
- `react_native.md` points to the rule. Metro without `CI=1` is already in its **Device testing**.

### 11. Reviewers save their own reports [18] (all seven reviewer agents, `skills/phase/references/review.md`, `skills/phase/references/plan.md`, `skills/quick-fix/SKILL.md`)

**Problem.** The reviewers return their report as their answer, and the session copies it into
`reviews/<agent>-YYYY-MM-DD-HHmm.md` by hand (LFPV phase 004). That copy costs context, and "verbatim"
depends on the copy.

**Rule.**
- Each reviewer agent gains the Write tool, for one file only: the report path the session gives it.
  It still never edits code, specs or plans, and it still returns its short verdict.
- When the reviewers finish, the session checks that `git status` shows no change except the report
  paths it handed out. Any other change is reverted and logged.

### 12. A fair speed check [6] (`practices/testing.md`, `skills/phase/references/review.md`, `agents/review-tests.md`, `templates/test-summary.md`)

**Problem.** In LFPV's phase 003, the speed rule compared p95 against the earlier report's numbers, which
came from another run on another day. Machine load alone can move p95 past the 20% line.

**Rule.**
- The speed check runs the previous code (the phase's base on `origin/dev`) and the new code in paired,
  alternating runs on the same machine, in one sitting: old, new, old, new, at least 5 pairs.
- It compares the medians. More than 20% slower on an API call's p95, or a Lighthouse score 5 or more
  points lower, still blocks.
- `summary.md` records the base commit, the number of pairs and both medians. The earlier report's
  numbers are context only.

### 13. Reports on Windows [7, 20] (`practices/testing.md`)

**Problem.** In LFPV, the first report run on Windows failed on setup (the Go version against `go.mod`,
bash on the PATH, the Go toolchain setting). In phase 004, the API and app Jest reports run at once hit
Jest's transform-cache EPERM lock.

**Rule.**
- The report command starts with a preflight that fails in seconds, with the fix in one line. It
  checks:
  - `go version` against `go.mod`, with `GOTOOLCHAIN=local` so no toolchain is downloaded;
  - bash on the PATH, with Windows paths passed into bash through `cygpath -u`;
  - the dependencies installed.
- Components' reports run one after another. Two Jest processes never run at once. If EPERM still
  appears, that run uses `--no-cache`.

### 14. A pre-flight before the owner's test [10, 13, 19] (`skills/phase/references/staging-test.md`)

**Problem.** In ETP's test, the phone could be offline or a test account missing, found only mid-test.
In LFPV's, a checkout switch left stale translations and bundle state. LFPV has no staging, so the local
stack, Metro and the phone needed restarting after each gap, with no word about low memory.

**Rule.** A new section, **Pre-flight**, runs before "ready for your test", and again when you come back
after the session waited or compacted:
1. the API (staging, or the local stack's API, DB and seed) answers its health check, and each test
   account in the message exists;
2. after a checkout switch, Metro is cold-started with file watching (`npx expo start --clear`) and the
   app is fully reloaded;
3. the phone shows in `adb devices` and `adb reverse` is up. If it needs wireless pairing, the
   ready-for-test message asks for the pairing code and port up front;
4. free memory is checked. Under 2 GB free, the message warns you, and the session stops what it
   started and no longer needs (an emulator, an old dev server).

The message reports each check in one line. A check that fails is fixed before you start, or it becomes
the first thing the message asks of you.

### 15. A fix that changes behaviour updates the test steps [21] (`skills/phase/references/review.md`, `skills/phase/references/staging-test.md`)

**Problem.** In LFPV's phase 004, re-reading the test scripts after a behaviour-changing fix was left to
memory. If a step is not re-read, you test against an expected result the fix changed.

**Rule.**
- A fix round (review or staging test) that changes owner-visible behaviour re-reads the affected
  features' test scripts in the spec and in `doc/features.yaml`.
- A step whose expected result no longer holds is updated in both. The sign-off PR lists the change in
  Calls I made, or, in a staging-test fix, the message before the retest says so.

## Release

- Version 1.5.0: `harness.go`, `.claude-plugin/plugin.json`, and a `CHANGELOG.md` section.
- `log` and `contrast` are built test first, with tests in `cmd/pal-harness`. The coverage gate stays
  at 80%.
- `content_test.go` gains `TestHarness150Rules`, which pins the new rules, the way 1.4.1's
  `TestRetro002Rules` does.
- Through pal-harness's own `dev` → `[HUMAN GATE]` `staging` → `main`, then the tags. `v1.4.2` goes on
  its own commit (`7a0821c`, already version 1.4.2), so the CHANGELOG's 1.4.2 entry is real. `v1.5.0`
  goes on the `main` merge commit.
- Once `v1.5.0` is tagged, each of the 21 captures is closed (discarded, as the 1.4.1 captures were),
  and the self-hosted-runner part of capture 2 is filed as a Pal Center product capture.

## Out of scope

- Re-pinning any project (the "pin 1.4.2" capture).
- Changing each project's CI files, bot workflows or report commands. Each project picks the rules up at
  its next phase that touches the area.
- A self-hosted Windows runner (now a Pal Center product capture).
- Pal Center reading new `ci` values: `ci` keeps `green | red | running | none`, and a spending-limit
  block is a note.
