# pal-harness 1.9.0: trial numbers, Pal Center in step with the pin, and phase 020's lessons

**Status:** Draft for the owner, 2026-11-22. All 9 questions answered "accept all" the same day.
**Source:** 10 harness notes raised in Pal Center (ai-workshop#48 to #57), mostly from Pal Center
phase 020's retro, worked in session HARNESS-work-9V36WY.
**Delivers:** pal-harness 1.9.0:
- one schema addition (`owner_stops:` in `phase-state.yaml`);
- one new check flag (`check --reader <version>`);
- one new reference file (`skills/phase/references/linux-check.md`);
- rule text for the rest.

It is a minor version, because of the new field. The `upgrade` command and the automatic re-pin
move to 1.10.0 (answer 1).

## Summary for the owner

1. **The veto-window trial gets numbers.** Each owner stop you answer adds one line to the phase
   state: its kind, how long it waited, whether it could have been a Company-mode decision, and how
   it ended. The retro reads those lines.
2. **Pal Center and the pin stop drifting apart.** The phase-state template stops writing optional
   keys that hold their default. `pal-harness check --reader <version>` warns when a file uses a
   field that an older reader doesn't know. Sessions look up which harness version the installed
   Pal Center reads, at phase start and at ship, and warn you when it is behind.
3. **Smaller plans, fewer review rounds.** A plan over 8 tasks (or about 30 KB) is split into parts
   that are reviewed one at a time. The plan reviewer must report everything in round 1.
4. **QA survives a cold start.** The QA pass warms the app up before the first screenshot and
   retries a first-load timeout once.
5. **Quieter builds.** Implementers stop their background work before the final report. Reports from
   finished tasks are ignored. Should-fix minors are fixed in the next task, not in one big wave at
   the end.
6. **A CI outage is not a fix round.** A job that failed from a package-mirror or network outage is
   re-run once on its own and logged as infra.
7. **A written Linux-check recipe** for Windows hosts: WSL with a new enough git, a tmpfs TMPDIR,
   Docker for Rust builds, and memory.
8. **Reviews check every ending.** A feature that sorts runs into outcomes needs a test for each way
   a run can end.

## Changes

Note numbers in brackets are the issue numbers in ai-workshop. Everything ships in one PR into
`dev`.

### A. The trial measure in the phase state [#48] (`state`, `templates/phase-state.yaml`, `skills/phase/SKILL.md`, `skills/phase/references/company-mode.md`, `agents/retro.md`)

**Problem.** 1.8.0 added the retro's **Owner stops** table, but the retro rebuilds it from the log
after the fact. There's nothing in the phase state that Pal Center or a later count can read, so the
veto-window rules can't be judged on numbers.

**Rule.** Answer 2.
1. **New optional field** `owner_stops:` in `phase-state.yaml`, a list. One entry is added when the
   owner's answer clears `waiting_on_owner`:

   ```yaml
   owner_stops:
     - {kind: spec-review, since: 2026-11-22T10:00:00+08:00, answered: 2026-11-22T11:30:00+08:00, could_decide: true, via: owner}
   ```

   | Key | Value |
   |---|---|
   | `kind` | one of the `waiting_on_owner` kinds |
   | `since` | the stop's `since` |
   | `answered` | when the answer came, not before `since` |
   | `could_decide` | `true` for a spec-review or findings stop with recommended answers and no money, key or public question (the retro's existing test), whether Company mode was on or not |
   | `via` | `owner` (answered in the session), or the `wait-decision` result: `approved`, `defaulted`, `changed`, `vetoed` |

   `check` validates every key. A `via` other than `owner` needs `could_decide: true`.
2. **Who writes it.** The phase skill's **Owner stops** step 5 (and so every quick fix) adds the
   entry in the same commit that clears `waiting_on_owner`. `company-mode.md` says that `via` is the
   `wait-decision` result.
3. **The retro** fills its **Owner stops** table from `owner_stops`. It falls back to the log only
   for a phase without the field. The count line stays the same.
4. **Not written** when the installed Pal Center reads an older harness (Change B3). The stop then
   stays in the log only, and the retro falls back.

### B. Pal Center and the pin agree on the phase state [#55, #56] (`templates/phase-state.yaml`, `state`, `cmd/pal-harness` check, `skills/phase/SKILL.md`, `skills/phase/references/ship.md`)

**Problem.** Pal Center reads phase state with the harness version in its own `go.mod`. When a pin
writes a field that version doesn't know, Pal Center calls the file unreadable. That happened with
`qa:` on Pal Center phase 021 (Pal Center 0.23.0 read with 1.6.0). Pal Center 0.27.1 reads with
1.8.0, so `qa:` is fine today, but `owner_stops` would break it again.

**Rule.** Answer 3 (a, b and c). Answer 4: no tolerant reader in this release.
1. **B1. The template leaves out optional keys.** The `qa: none` line becomes a comment that names
   the key and its values. `owner_stops` appears only as a comment. **Saved state** gains one line:
   an optional key (`qa`, `owner_stops`) is written only when it holds a non-default value.
2. **B2. `pal-harness check --reader <version>`.** The `state` package records which harness version
   added each field:
   - everything present when `state` arrived: 1.3.0;
   - `check` in feature results and `qa` in phase state: 1.8.0;
   - `owner_stops`: 1.9.0.

   With `--reader`, check also prints one warning per field that a `doc/features.yaml` or
   `specs/*/phase-state.yaml` file actually uses and that is newer than the reader, for example:

   `warning: specs/021-x/phase-state.yaml: owner_stops needs harness 1.9.0; a reader on 1.8.0 calls this file unreadable`

   Warnings don't change the exit code. A version that doesn't parse is exit 2. Without `--reader`,
   check behaves as today.
3. **B3. Sessions look up the reader.** At phase start (and resume) and at ship:
   1. take `Pal Center version: X` from the session-start lines;
   2. read the pal-harness version in Pal Center's `daemon/go.mod` at tag `vX`:
      `gh api "repos/althenlimzixuan/pal-center/contents/daemon/go.mod?ref=vX" -H "Accept: application/vnd.github.raw"`;
   3. run `pal-harness check --reader <that version>`.

   If any step fails (no version line, no `gh` access, no tag), the session logs
   `reader check: not available (<why>)` and goes on.

   On a warning:
   - at phase start, the session leaves the newer optional keys out (A4) and tells the owner in one
     line: `Pal Center X reads harness Y; update Pal Center to see owner_stops`;
   - at ship, the same line goes in the done message.
4. **Release order**, written in the CHANGELOG: Pal Center moves its harness dependency to 1.9.0 and
   ships before any project re-pins to 1.9.0. Both are steps you choose, outside this release.

### C. Plan size and one-round plan reviews [#49] (`skills/phase/references/plan.md`, `agents/review-plan.md`, `templates/plan.md`)

**Problem.** Pal Center phase 020's plan was 75 KB with 11 tasks. It took 3 review rounds
(1 major, then 8, 7 and 3 minors), and the round-3 minors were fixed after the last allowed round.

**Rule.** Answer 5.
1. **Parts.** A plan over 8 tasks, or over about 30 KB, is written in parts of up to 8 tasks each:
   - `plan.md` holds the summary and coverage for the whole phase, plus Part 1's tasks;
   - `plan-2.md`, `plan-3.md` and so on hold the later parts' tasks, numbered on from the part
     before.

   It stays one phase, one branch per repo and one sign-off. `tasks.total` counts every part.
2. **One review per part.** `pal-review-plan` reviews each part, reading `plan.md`'s summary for
   context. Part 1's review also runs the whole-phase checks (coverage, size, the earlier majors).
   Reports are named `pal-review-plan-partN-YYYY-MM-DD-HHmm.md`. Every part passes its review before
   the build starts, and the parts are built in order.
3. **Everything in round 1.** The reviewer runs every check over the whole part and reports every
   finding it sees, however small, in round 1, holding nothing back for a later round. A later round
   checks only the fixes and the text they changed. A new finding on unchanged text is raised there
   only when it is critical.
4. The phase-size rule (about one working day, otherwise an owner question about splitting the
   phase) stays as it is.

### D. QA warm-up [#50] (`skills/phase/references/qa.md`, `templates/screens.spec.ts`)

**Problem.** Phase 020's first QA screenshot run timed out on a cold Vite start and had to be run
again.

**Rule.** Answer 6.
1. Before the first step, the QA pass loads the app's first page once and waits for it to render,
   without saving a screenshot. A dev server compiles on its first load.
2. A step whose first page load times out is retried once, and `summary.md` notes
   `cold start: retried`. A second timeout fails the step.
3. `screens.spec.ts` gains the same warm-up: one load of the first page in `beforeAll`, with a
   longer timeout.
4. Pal Center's own `npm run qa` script is Pal Center code. It gets the warm-up as a Pal Center quick
   fix after its re-pin, not in this release.

### E. Background work and finished tasks [#51] (`skills/phase/references/subagents.md`)

**Problem.** In phase 020, implementers left background work running that kept re-sending reports
after their tasks were done.

**Rule.**
1. **The brief** gains an item: before the final report, the implementer finishes or stops every
   background command, Monitor and watcher it started, and says in the report that none is still
   running.
2. **The controller** gains a rule: a report from a task already marked done is ignored (not acted
   on and not answered). A second one gets TaskStop.

### F. CI outages are re-run, not fixed [#52] (`practices/devops_cicd.md` **Waiting on CI and merging**, `skills/phase/references/build.md`)

**Problem.** Phase 020's Linux job hit a GitHub Ubuntu mirror outage on the final commit. The 28-minute
job was re-run by hand, and the tests review waited.

**Rule.** Answer 7.
1. After reading why a job failed, the session checks whether the failing step's log shows an outage
   sign:
   - apt `Failed to fetch` or `Hash Sum mismatch`;
   - `Could not resolve host`;
   - `Connection timed out` or `Connection reset`, `ETIMEDOUT`, `ECONNRESET`;
   - an HTTP 5xx from a package registry, mirror or module proxy.
2. If it does, the session runs `gh run rerun <run-id> -R <owner/repo> --failed` once and watches the
   run again. The log gets `infra re-run: <job> (<sign>)`. It is not a fix round, and nothing is
   pushed.
3. If the re-run fails with an outage sign again, the session tells the owner in one line and runs
   the CI locally (**CI runs and minutes**). A green local run counts as the PR's CI for the merge
   gates, as it does for a billing block.
4. This applies to every CI watch: build, fix now, quick fix, sign-off and ship.

### G. The Linux-check recipe [#53] (new `skills/phase/references/linux-check.md`; pointers from `build.md` and `skills/quick-fix/SKILL.md`)

**Problem.** Phase 020 had to work out on its own how to prove Linux code on a Windows PC. WSL's
git was too old, it needed a tmpfs TMPDIR, Rust needed Docker, and memory ran short.

**Rule.** Answer 8. The new reference is loaded only when a Windows host needs a Linux proof
(`!windows` Go files, `#[cfg(unix)]` Rust, a Linux CI job). It holds:
1. **Cheap first.** From Windows, run `GOOS=linux golangci-lint run ./...` and
   `GOOS=linux go vet ./...`. A Windows lint skips `!windows` files.
2. **WSL.** Check it with `wsl.exe -l -v`. git must be 2.28 or later (`git init -b`); Ubuntu 20.04
   ships 2.25. Installing a newer one from the git-core PPA needs `sudo`, so it is an owner-run
   command, run once. Until then, the tests that use `git init -b` are listed as known WSL failures,
   and CI is their proof.
3. **The run.** Run from the worktree with TMPDIR on a Linux-side tmpfs, never under `/mnt/<drive>`
   (Windows drives don't keep Unix permissions or sockets):
   `wsl.exe -d Ubuntu -- bash -lc 'export TMPDIR=$(mktemp -d -p /dev/shm) && cd "$(wslpath -a "<worktree>")/<dir>" && GOTOOLCHAIN=local GOFLAGS=-p=1 GOMEMLIMIT=2GiB go test <packages>'`.
4. **Rust and Tauri.** WSL has no Rust; use Docker Desktop with Linux containers:
   `docker run --rm -m 6g -v "<worktree>:/src" -w /src/<dir> rust:1-bookworm bash -c "<apt deps> && CARGO_TARGET_DIR=/tmp/target cargo clippy … && CARGO_TARGET_DIR=/tmp/target cargo test …"`.
   The target folder stays inside the container.
5. **Memory.** Run `pal-harness mem --min 4GiB` before a Docker Rust build, and `--min 2GiB` before
   WSL tests. WSL's own limit is `memory=` in `%UserProfile%\.wslconfig`, the owner's file, which the
   session only suggests changing. When memory is short, skip the heavy local run and log it.
6. **CI as the proof.** When WSL or Docker is missing, or memory is short, the task's log line says
   `Linux proof: CI's Linux job`, and the first red run there is fixed by the same task's rules.

### H. Should-fix minors go into the next task [#54] (`skills/phase/references/subagents.md`, `skills/phase/references/build.md`)

**Problem.** Phase 020's task reviews deferred many minors marked should-fix (5, 5, 2, 8 …). They all
landed in one final fix wave of 8 commits, which made the last re-review bigger.

**Rule.**
1. After task K's review, each should-fix minor not fixed in its own rounds goes on a **Carry-over**
   list in task K+1's brief. The implementer fixes them first, in their own commit
   (`Fix Task K review minors`), and task K+1's review checks them. It is not a fix round.
2. The last task's carry-overs go to one fixer before the whole-branch review.
3. An inline build does the same: fix them before starting the next task.
4. Minors that aren't should-fix still go to `doc/later.md` under **Deferred minors**, as today.

### I. Every ending tested [#57] (`skills/phase/references/subagents.md` section 3, `agents/review-tests.md`)

**Problem.** Features that sort runs into outcomes kept missing an ending, such as an owner stop or a
restart, and each miss cost a fix round.

**Rule.** Answer 9. The task reviewer's checks and `pal-review-tests` gain **Every ending tested**.
For a feature that sorts runs, sessions or jobs into outcomes (a status, a result, an end state):
1. list every way one can end: start failed, owner stop, restart mid-run, idle, waiting, cancelled,
   timed out, crashed or killed, plus any ending the feature defines itself;
2. match each to a test that drives it and checks the outcome.

An ending with no test is a **major** finding.

## Release

- **Version 1.9.0:**
  - `harness.go`, `.claude-plugin/plugin.json` and a `CHANGELOG.md` section, which states the
    release order (B4);
  - the README command table (`check --reader`);
  - `templates/ci.yml` names `@v1.9.0`.
- **Tests:**
  - `TestHarness190Rules` pins the new rule phrases;
  - `TestContentComplete` lists `linux-check.md` and keeps the line caps (the phase skill is at 249
    of 250 lines, so its edits are rewrites in place);
  - `state` gets tests for `owner_stops` and for which version added each field;
  - the check command gets tests for `--reader`: a warning for a newer field, none for an older
    reader that knows it, exit 2 for a bad version;
  - the template test checks that `qa:` is no longer a live key.
- **One PR into `dev`** with one Closes line per note (#48 to #57). It merges on green CI after the
  merge guard. One `[HUMAN GATE]` `dev` → `staging` PR follows, which you merge. Then `staging` →
  `main`, the `v1.9.0` tag on the merge commit, and the CHANGELOG entry. Codex review is skipped
  (`pal-review` knows only workspace projects), and the PR says so.
